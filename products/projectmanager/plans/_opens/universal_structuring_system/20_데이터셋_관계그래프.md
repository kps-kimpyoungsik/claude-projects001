# 20. 데이터셋 관계 그래프 — 많아진 데이터셋을 서로 참조하게 만들기

초판 2026-09-19 | 상태: **설계 초안** | 상위: [`00_뼈대설계서.md`](00_뼈대설계서.md) §8 확장
선행: DDS `01_설계서.md` §3·§4.2·§8.3 (관계축 초판 설계 — **구현 대기 Phase 3·5·6**)

---

## 0. 먼저 — 판정 확정

요청의 "지식그래프 vs GraphQL"에 답한다. **둘은 경쟁 관계가 아니라 다른 층이다.**

| | 지식그래프 | GraphQL |
|---|---|---|
| 정체 | **데이터 모델** — 무엇과 무엇이 어떻게 연결됐는가 | **API 질의 문법** — 클라이언트가 필요한 필드만 요청 |
| 요청("관계 맺어 필요시 참조")에 답하는가 | **그렇다 — 이게 답이다** | 아니다. 관계가 없으면 GraphQL로도 못 따라간다 |
| 판정 | **채택.** 단 *저장 엔진*은 관계 테이블로 시작(§5) | **미채택.** REST 3개로 충분(§4). 근거는 §6 |

> 흔한 오해 하나를 먼저 끊는다 — **GraphQL의 "Graph"는 지식그래프가 아니다.**
> GraphQL은 스키마 기반 조회 문법이고, 관계를 *만들어 주지 않는다*. 관계를 만드는 것은
> 아래 §2의 엣지 생성 3경로다. **관계가 있으면 REST로도 탐색되고, 관계가 없으면
> GraphQL로도 탐색 못 한다.** 그래서 이 문서는 전부 "관계를 어떻게 만들고 믿을 것인가"다.

## 1. 실측 — DDS가 이미 설계한 것 / 비어 있는 것

### 1.1 이미 있다 (설계 완료, 구현 대기)

| 자산 | 내용 | 상태 |
|---|---|---|
| `standard_relation` | 표준 간 관계 **정의** (사람 승인). "결함은 화면에 달린다" | **구현 완료** (Phase 2) |
| `dataset_link` | 데이터셋 간 관계 **인스턴스** (Jaccard 추론, fk/same_entity/derived_from/time_aligned) | 설계만 (Phase 5) |
| `dataset_facet` | 5축 태그 (domain·area·role·context·topic) + confidence·evidence | 설계만 (Phase 3) |
| `dataset_view` | 저장된 질의 = 동적 데이터셋. 조인 경로 최대 2홉 | 설계만 (Phase 6) |
| **관계 이원화 원칙** | **"추론이 정의를 이기지 않는다"** — 표준 관계 먼저, 없을 때만 추론 링크 | 설계 확정(§8.3) |
| 근거 반환 | 뷰 응답에 `sources[]`·`linksUsed[]`·`warnings[]` 필수 | 설계 확정 |

> **요청하신 것의 상당 부분이 이미 설계돼 있다.** 여기서 새 모델을 그리면 중복 정본이 된다
> (T39 CRZ). 이 문서는 **비어 있는 칸만** 채운다.

### 1.2 비어 있다 — 이 문서가 채우는 것

| # | 결핍 | 왜 문제인가 |
|---|---|---|
| **R1** | **노드가 `dataset` 하나뿐** | 표준·용어·**작업**은 속성으로만 존재한다. "이 작업에서 뭘 썼나"를 물을 대상이 없다 |
| **R2** | **작업(case) 축 부재** | 요청의 5축(분야·영역·**작업**·관계·역할) 중 '작업'에 대응하는 것이 DDS에 없다 |
| **R3** | **사용 이력이 관계가 되지 않음** | 관계 생성이 Jaccard 값겹침 **하나**에 의존. 값이 안 겹치는 업무적 연결은 영원히 못 잡는다 |
| **R4** | **관계 탐색 비용 미설계** | N개 데이터셋의 전수 비교는 N². 수십 개일 땐 안 보이고 수백 개에서 터진다 |
| **R5** | **관계의 정확도 측정 없음** | 틀린 관계가 조인에 끼면 결과가 조용히 오염된다. 관계도 `precision` 대상이어야 한다 |
| **R6** | **부정 관계(아님) 표현 불가** | 사람이 "이 둘은 관계 없다"고 해도 다음 배치가 같은 링크를 또 만든다 |

## 2. 그래프 모델 — 노드 5종 · 엣지 7종

### 2.1 노드 (R1·R2 해소)

**새 테이블을 만들지 않는다.** 이미 있는 표의 행이 곧 노드다 — 그래프는 *관점*이지 저장소가 아니다.

| 노드 | 실체(기존 테이블) | 요청의 축 |
|---|---|---|
| `dataset` | `dataset` | — |
| `standard` | `standard_dataset` (STD/DOM) | 역할(무엇의 표인가) |
| `term` | `vocab_term` (분야·영역·주제 값 포함 — `facet_vocab`은 폐기됨) | 분야 · 영역 |
| **`case`** | **`struct_case`** (USS 신규 — 정형화 작업 1건) | **작업** |
| `column` | `dataset_column` | 컬럼 의미(id/time/measure…) |

> **데이터셋의 역할**(분야 안에서 master·code·transaction·plan·snapshot·bridge 중 무엇인가)은
> 노드 속성으로 [`21_데이터셋_역할축.md`](21_데이터셋_역할축.md)에서 정의한다 — 그 역할이
> §4 탐색의 **조인 방향·집계 대상·기본 제안**을 바꾼다(21 §5).

### 2.2 엣지 — **증거 등급이 곧 신뢰 서열이다**

| 엣지 | from → to | 생성 경로 | **증거 등급** |
|---|---|---|---|
| `produced` | case → dataset · projection | **기계 기록** (작업이 만들었다) | **E1 사실** |
| `derived_from` | dataset → dataset | **기계 기록** (뷰 물질화·변환 이력) | **E1 사실** |
| **`used_in`** | **dataset → case** | **기계 기록** (그 작업에서 실제로 참조됨) | **E1 사실** |
| `relates_to` | standard → standard | 사람 정의 + 승인 (`standard_relation`) | **E2 정의** |
| `instance_of` | dataset → standard | 바인딩 (`dataset.std_id`, bind_ratio) | E2/E3 (확신도별) |
| `tagged` | dataset·column → term | 분류 (`dataset_facet`) | E3 추론 |
| `fk` / `same_entity` | column → column | Jaccard 값겹침 (`dataset_link`) | **E3 추론** |
| `not_related` | 임의 → 임의 | **사람이 명시적으로 부정** (R6) | **E0 거부권** |

**서열 규칙 — DDS §8.3 "추론이 정의를 이기지 않는다"의 일반화:**

```
E0 부정(사람) > E1 사실(기계기록) > E2 정의(사람승인) > E3 추론(통계·임베딩)
```

- 탐색·조인 계획은 **높은 등급부터** 쓴다. E3는 위 셋이 비었을 때만.
- **E0는 절대 거부권**이다. `not_related`가 있으면 어떤 배치도 그 링크를 다시 만들지 않는다(R6).
  — DDS의 "human은 덮이지 않는다"를 *관계*에 적용한 것. 새 원칙이 아니다.

## 3. R3 해소 — **사용 이력이 가장 강한 관계 신호다**

> 이것이 이 문서의 핵심 주장이다.

DDS의 관계 추론은 **Jaccard 값겹침** 하나다. 이건 두 약점이 있다:

1. **못 잡는다** — 코드 체계가 다르면 값이 안 겹친다. `계약번호 C-2026-01`과 `프로젝트코드 PRJ-88`이
   업무상 같은 건을 가리켜도 Jaccard는 0이다. **업무 관계의 상당수가 여기 걸린다.**
2. **헛잡는다** — `상태` 컬럼끼리는 값이 `진행/완료`로 크게 겹친다. 관계가 아니라 **코드집합 공유**다.

**대안은 새 알고리즘이 아니라 이미 발생하는 사실을 기록하는 것이다:**

```
사람이 견적서 작업(case A)에서 [단가표, 지난계약서, 인력현황] 3개를 참조했다
   → used_in 엣지 3개가 자동으로 생긴다 (작업하면서 공짜로)
   → 이 셋은 "함께 쓰인다"는 관계다.  값이 안 겹쳐도 성립한다.
   → 다음에 비슷한 case가 오면 "지난번엔 이 셋을 같이 썼습니다" 를 제안할 수 있다
```

| 신호 | 비용 | 잡는 것 | 못 잡는 것 |
|---|---|---|---|
| Jaccard 값겹침 (기존) | N² 비교 | 같은 키를 쓰는 표 | 코드 체계가 다른 업무 연결 |
| **사용 이력 (신규)** | **0 — 작업하면 쌓인다** | **업무적으로 함께 쓰이는 표** | 아직 아무도 안 써본 신규 데이터셋 |

**둘은 상보적이다.** Jaccard는 신규 데이터셋의 **콜드 스타트**를 담당하고, 사용 이력은 시간이
갈수록 정확해진다. 그래서 §2.2에서 `used_in`을 E1(사실)로, Jaccard를 E3(추론)로 나눴다.

**동시사용 가중치** (같은 case에 함께 등장한 횟수):

```
cooccur(A,B) = Σ_case  w(case)      w = 최근성 감쇠(최근 작업일수록 큼)
관련도 점수  = Σ 엣지별 (등급가중 × 최근성 × 사용빈도)
```

임계·가중치는 손으로 정하지 않고 **§7 측정에 반응**해 조정한다(00 뼈대 §7.2 원칙 그대로).

## 4. 참조 — "필요시 참조"의 실체는 질문 3종

관계를 만드는 것만으로는 아무 일도 안 일어난다. **어디서 당겨 쓰는지**를 정해야 값을 한다.

| 질문 | 쓰는 엣지 | 엔드포인트 | 응답 |
|---|---|---|---|
| **Q1. 이 데이터셋과 관련된 건?** | 전 엣지, 1~2홉, 점수순 | `GET /api/graph/neighbors/{nodeId}?hops=2&limit=20` | `[{node, edgeType, evidenceLevel, score, why}]` |
| **Q2. 이 작업에 뭘 쓰면 되나?** | `used_in` (유사 case) + `tagged`(분야·영역 일치) | `GET /api/graph/suggest?caseId=&stdId=&domain=` | 후보 + **"유사 작업 3건에서 함께 사용됨"** 근거 |
| **Q3. 이 값의 근거는?** | 역방향 `produced`→`fact`→`fragment`→`doc` | `GET /api/graph/provenance/{factId}` | 원본 문서·좌표까지 (00 뼈대 I1) |

- **Q2가 요청의 목적지다.** 데이터셋이 많아졌을 때 사람이 못 하는 일이 "**무엇이 있는지 아는 것**"
  이고, 그걸 **비슷한 과거 작업**으로 답한다.
- **모든 응답에 `why`(왜 관련 있다고 보는가)를 붙인다** — 근거 없는 추천은 안 쓰이거나,
  더 나쁘게는 검증 없이 쓰인다. DDS 뷰 응답의 `sources`/`linksUsed` 규격과 동일하다.
- **REST 3개면 끝난다.** 이것이 §6에서 GraphQL을 미채택하는 실질 근거다.

```
GET  /api/graph/neighbors/{nodeId}      이웃 탐색
GET  /api/graph/suggest                 작업 기반 추천
GET  /api/graph/provenance/{factId}     근거 역추적
POST /api/graph/edges                   수동 관계 추가 (source=human, E2)
POST /api/graph/edges/negate            "관계 아님" 표시 (E0, R6)
POST /api/graph/discover                Jaccard 탐색 실행 (§5 스코프 제한 적용)
```

## 5. R4 해소 — 규모별 전략 (N² 폭발 방지)

### 5.1 탐색 스코프를 좁힌다 — 전수 비교하지 않는다

Jaccard 전수 비교는 데이터셋 N개 × 컬럼 C개에 대해 `(N·C)²`다. 실제로는 **거의 다 무의미한 비교**다.

| 가지치기 | 규칙 | 근거 |
|---|---|---|
| P1 역할 제한 | `role ∈ {id, ref}` 컬럼끼리만 비교 | 조인 가능한 것은 식별자뿐. `상태`끼리 겹치는 건 관계가 아니다 |
| P2 도메인 제한 | 같은 `domain` 또는 `standard_relation`이 존재하는 표준 쌍만 | 정의가 있는 곳에 인스턴스가 있다 |
| P3 카디널리티 | 고유값 < 3 또는 > 행수의 99%인 컬럼 제외 | 상수열·완전유일열은 신호가 없다 |
| P4 증분 | **새로 들어온 데이터셋 × 기존 전체**만 비교 (기존끼리 재비교 없음) | 관계는 한 번 정해지면 안 변한다 |

→ 실질 비교 수가 `N·(id컬럼 수)` 수준으로 떨어진다.

### 5.2 저장 엔진 — 지금은 테이블, 승격은 조건부

| 규모 | 엔진 | 탐색 방법 |
|---|---|---|
| **~ 200 데이터셋 / ~2,000 엣지** | **관계 테이블** (`dataset_link` + `standard_relation` + `case_usage`) | 재귀 CTE 2홉. **현재 여기** |
| 200~2,000 / ~20,000 엣지 | 동일 + **2홉 이웃 사전계산 테이블** | 배치로 이웃 캐시 갱신 |
| 그 이상, 또는 **4홉+ 탐색이 상시 필요** | **PostgreSQL AGE**(그래프 확장) 우선 검토 → 부족하면 Neo4j | Cypher |

**승격 조건을 수치로 못 박는 이유**: DDS `00_연구조사` §3이 이미 "Neo4j 미채택 — 관계
카디널리티 수십 규모, 관계 테이블 1개로 충분"으로 판정했다. **그 판정을 뒤집으려면
실측이 먼저다.** 느낌으로 컴포넌트를 늘리지 않는다.

> **AGE를 Neo4j보다 먼저 보는 이유**: 이미 PostgreSQL을 운영 중이다(`project-pm-manager-db`).
> 확장 하나가 운영 컴포넌트 +1보다 싸다. 같은 트랜잭션 안에서 관계와 데이터가 함께 움직인다.

## 6. GraphQL 미채택 — 근거

| 검토 항목 | 판정 |
|---|---|
| "필요한 필드만 받고 싶다" | §4의 3개 엔드포인트가 이미 목적별 응답을 준다. 과다 전송 문제가 **측정된 적 없다** |
| "클라이언트가 그래프를 자유 순회" | **오히려 위험.** 순회는 증거 등급 가중·권한·홉 제한 판단이 필요하다 — 서버가 해야 할 일이다 |
| 도입 비용 | 스키마 정의 + N+1 해결(DataLoader) + 권한 계층 + 기존 REST 40여 개와 이중 유지 |
| 기존 자산 | REST + `ApiExceptionHandler` + API Key 필터가 이미 동작 |

**재검토 조건**: 외부 시스템이 이 그래프를 소비하기 시작하고, 클라이언트마다 필요한 필드가
달라 엔드포인트가 **10개를 넘어갈 때**. 그 전에는 REST가 짧다.

## 7. R5·R6 해소 — 관계도 측정하고, 거부할 수 있어야 한다

**관계는 틀린다.** 틀린 관계가 조인에 끼면 결과가 **조용히** 오염된다 — 에러가 안 나서 더 위험하다.

| 장치 | 내용 |
|---|---|
| **관계 gold set** | 사람이 확인한 관계 50건을 `gold=true`로 고정. 00 뼈대 §7.1과 같은 규격 |
| **`link_precision`** | `struct_metric`에 열 1개 추가 — 자동 생성 관계가 gold 대비 맞은 비율 |
| **조인 경고** | 뷰 실행 시 E3(추론) 링크를 쓰면 응답 `warnings`에 반드시 표기 (DDS 규격 그대로) |
| **부정 엣지** | `not_related` = E0 거부권. 재탐색이 덮지 못한다 (R6) |
| **홉당 확신 감쇠** | 2홉 경로의 확신도 = 두 엣지 확신도의 **곱**. 멀어질수록 약해지는 것이 정상이다 |

**임계 자동 조정**: `link_precision`이 떨어지면 Jaccard 임계를 올린다(링크를 덜 만든다).
올라가면 내린다. **손으로 0.3을 정하지 않고 측정에 반응하게 한다** — 00 뼈대 §7.2와 같은 원리.

## 8. 데이터 모델 — 신규 1테이블 + 컬럼 3개

DDS 설계분(`dataset_link`·`dataset_facet`·`dataset_view`)은 그대로 구현하고, 여기에 더한다.

| 신규 | 내용 |
|---|---|
| **`case_usage`** | `case_id, node_type, node_id, usage(input/reference/output), used_at` — **R2·R3의 실체.** `used_in`·`produced` 엣지가 여기서 나온다 |

| 컬럼 추가 | 대상 | 용도 |
|---|---|---|
| `evidence_level` | `dataset_link` | E0~E3 (§2.2 서열) |
| `negated_by` · `negated_at` | `dataset_link` | E0 거부권 (R6) — 행을 지우지 않는다(재생성 차단 근거가 사라지므로) |
| `link_precision` | `struct_metric` | R5 측정 |

> **`case_usage` 하나가 R1·R2·R3를 동시에 푼다.** 작업을 노드로 세우고(R1·R2),
> 사용 이력을 관계로 만든다(R3). 그리고 **기록 비용이 0이다** — 작업이 데이터셋을 읽을 때
> 한 줄 남기면 끝이다.

## 9. 단계 계획 — **정본은 [`01_단계지도.md`](01_단계지도.md)**

> **정정 2026-09-19**: G3 는 DDS Phase 5 와 **같은 작업**이다(둘 다 `dataset_link` 생성).
> 별도로 세면 이중 계상된다. 또 G3·G4 는 현재 데이터셋 **9개** 실측상 검증 대상이 없어
> **보류**(착수 조건: 데이터셋 30개 이상). 착수분은 **G1(1인일)뿐**이다.

## 9-A. G단계 내용 정의

| Phase | 내용 | 선행 | 인일 |
|---|---|---|---|
| **G1** | `case_usage` + `used_in`/`produced` 자동 기록 (L3·L4 경로에 1줄씩) | U3 | **1** |
| **G2** | `GET /neighbors` + `GET /provenance` (E1·E2 엣지만 — 이미 있는 관계로) | G1 | 2 |
| **G3** | DDS Phase 5 구현 — `dataset_link` Jaccard 탐색 + §5.1 가지치기 4종 | U3 | 4 |
| **G4** | `GET /suggest` (유사 case 기반 추천) + `why` 근거 | G1·G3 | 3 |
| **G5** | E0 부정 엣지 + `link_precision` 측정 (§7) | G3·U5 | 2 |
| G6 | 2홉 이웃 사전계산 (규모 임계 도달 시에만) | 측정 | 조건부 |
| G7 | AGE 이전 (§5.2 조건 도달 시에만) | 측정 | 조건부 |

**G1이 1인일이고 가장 먼저인 것이 핵심이다.** 사용 이력은 **지금부터 안 쌓으면 과거를 복원할 수
없다.** 추천(G4)은 나중에 만들어도 되지만, 그 재료인 기록은 **가장 먼저** 시작해야 한다.

## 10. ADR

| # | 결정 | 대안 | 왜 |
|---|---|---|---|
| G-A1 | 그래프는 **관점**, 노드는 기존 테이블의 행 | 노드 테이블 신설 | 같은 것을 두 곳에 두면 갈라진다(T39 CRZ). `facet_vocab` 폐기 선례 그대로 |
| G-A2 | **증거 등급 4단(E0~E3)** 서열로 탐색 | 확신도 숫자 하나로 정렬 | 출처가 다른 확신도는 비교 불가다. 기계 기록 0.7과 추론 0.9는 같은 축이 아니다 |
| G-A3 | **사용 이력을 E1(사실)로** | Jaccard 단일 신호 | 값이 안 겹치는 업무 관계를 유일하게 잡는다. 비용 0 |
| G-A4 | 부정 엣지는 **행 삭제가 아니라 표시** | 링크 삭제 | 삭제하면 다음 배치가 같은 링크를 또 만든다 — 사람이 같은 일을 반복하게 된다 |
| G-A5 | 저장 엔진 승격은 **수치 조건** | 처음부터 그래프 DB | DDS 미채택 판정을 실측 없이 뒤집지 않는다. AGE 우선(컴포넌트 +0) |
| G-A6 | GraphQL 미채택 | 지금 도입 | 관계 탐색은 서버가 가중·권한을 판단해야 한다. REST 3개로 끝난다 |
| G-A7 | 2홉 확신도 = **곱** | 경로 최대값·평균 | 멀어질수록 약해지는 것이 관계의 성질이다. 곱이 아니면 3홉 헛관계가 상위에 뜬다 |

## 11. 하지 않는 것

| 항목 | 이유 |
|---|---|
| 전 데이터셋 자동 관계 생성 후 방치 | 검증 안 된 관계 수천 개는 자산이 아니라 **소음**이다. §5.1 가지치기 + §7 측정이 짝으로 가야 성립 |
| 관계 자동 승격(추론 → 정의) | E3가 스스로 E2가 될 수 없다. 사람 승인만이 등급을 올린다 |
| 3홉 이상 기본 탐색 | 확신도 곱이 급감해 신호보다 잡음이 많다. 필요 시 명시 요청(`hops=3`)으로만 |
| 그래프 시각화 화면 | **예쁘지만 안 쓰인다.** 실제 쓰이는 것은 §4의 질문 3종이다. 요구가 생기면 그때 |
