# 21. 데이터셋 역할축 — 분야 안에서 이 정보가 맡는 역할

초판 2026-09-19 | 상태: **설계 초안**
상위: [`00_뼈대설계서.md`](00_뼈대설계서.md) · 짝: [`20_데이터셋_관계그래프.md`](20_데이터셋_관계그래프.md) §12 결정필요 해소

---

## 1. 무엇을 정하는가

> **같은 분야 안에서도 데이터셋마다 맡는 역할이 다르다.**
> 어떤 표는 *대상의 목록*이고(화면목록·인력), 어떤 표는 *일어난 일의 기록*이며(결함·투입),
> 어떤 표는 *값의 뜻 사전*이고(코드표·단가표), 어떤 표는 *시점 고정 사본*이다(주차 스냅샷).
> 이 역할을 모르면 **조인 방향도, 집계 대상도, 무엇을 먼저 참조해야 하는지도** 매번 틀린다.

---

## 2. 먼저 — 이름 충돌 정리 (T39 CRZ 선행)

DDS에 **이미 `dataset_role` 이라는 이름이 있다.** 그런데 **뜻이 다르다.**

| | DDS `dataset_role` (06 §3 PSR) | **이 문서의 역할축** |
|---|---|---|
| 묻는 것 | "같은 것을 담은 표가 여럿일 때 **어느 게 정본인가**" | "이 표가 분야 안에서 **무슨 일을 하는가**" |
| 값 | `primary` / `secondary` / `quarantine` + `subset`·`older_version`·`derived`·`variant` | `master`·`code`·`transaction`·`plan`·`snapshot`·`bridge` |
| 축의 성질 | **중복 서열** — 인스턴스끼리 겨룬다 | **기능 분류** — 표준의 성질이다 |
| 붙는 대상 | 데이터셋(인스턴스) | **표준**(standard_dataset), 데이터셋은 상속 |

**두 축은 직교한다** — "정본인 마스터"도 "부본인 마스터"도 있다. 합칠 수 없다.

> **조치**: DDS `dataset_role` 은 **아직 구현 전**(`schema.sql` grep 결과 테이블 없음, 설계 문서에만 존재)
> 이므로 지금 이름을 바꿀 수 있다. **제안: `dataset_role` → `dataset_canon`** (정본 지위).
> 이 문서의 것은 `data_role` 로 둔다.
> **이 rename은 DDS 06 문서의 정본을 건드리므로 이 문서에서 단독 확정하지 않는다** — §7 결정 대상.
> 확정 전까지는 **두 이름을 섞어 쓰지 않는다**(같은 단어가 두 뜻이면 반드시 사고가 난다).

## 3. 역할 6종 — 실측에서 뽑았다

상상으로 분류하지 않았다. **이 프로젝트에 실제로 있는 표**를 놓고 갈랐다.

| `data_role` | 뜻 | **이 프로젝트 실례** | 판정 신호 |
|---|---|---|---|
| **`master`** 기준정보 | 대상의 목록. 변경이 드물다 | `ia_screen`(화면 252) · `staffing`(투입인력) | id 유일 ∧ 결측 0 · 행 증가율 낮음 · **다수가 참조(fan-in 높음)** |
| **`code`** 코드·분류·단가 | 값의 *뜻*을 정의 | `vocab_term.code_values` · 견적 단가표 | 행 적음(≤200) ∧ 컬럼 2~4 ∧ **다른 표의 category 값 집합과 일치** |
| **`transaction`** 거래·실적·사건 | 일어난 일 1건 = 1행 | `defect`(151) · `upload_batch` | `time` role 필수 ∧ 행이 계속 는다 ∧ `measure` 보유 |
| **`plan`** 계획·기준선 | 목표값. 실적과 **대비**된다 | `wbs_task`(계획 시작/종료 + 구성비) | transaction과 같은 표준 ∧ 미래 날짜 비중 ↑ ∧ 버전·기준일 보유 |
| **`snapshot`** 이력·시점 사본 | 그때의 상태를 고정 | 주차별 진척 아카이브 | 같은 표준의 `older_version` 다수 ∧ 기준일이 사실상 키 |
| **`bridge`** 매핑·연결 | 두 대상을 잇기만 한다 | (현재 없음 — 화면↔결함 매핑표가 생기면) | 컬럼 대부분이 `id`/`ref` role ∧ **자체 measure 없음** |
| `unknown` | 판정 불가 | — | **숨기지 않는다.** 화면에 "역할 미정"으로 노출 |

**6종으로 닫는다.** DDS가 6축을 닫은 것과 같은 이유다 — 값이 늘면 규칙과 화면이 동시에 무너진다.
새 역할이 필요해 보이면 먼저 **위 6종 중 하나의 변종이 아닌지** 검증한다.

### 3.1 "분야에서도" — 역할은 분야 안에서 상대적이다

같은 `인력현황`이 **인사 분야**에서는 `master`(사람의 목록)지만, **원가 분야**에서는
단가를 끌어오는 `code`에 가깝다. 역할이 절대값이 아니라는 뜻이다.

**기존 구조가 이미 이걸 푼다 — 새 장치를 만들지 않는다:**

```
standard_dataset( std_id, domain, ... , data_role )   ← 역할은 표준에 붙는다
dataset( dataset_id, std_id, ... )                    ← 인스턴스는 상속받는다
```

- `standard_dataset` 에 **이미 `domain` 컬럼이 있다.** 역할을 표준에 붙이면
  **(분야, 표준) → 역할**이 자동으로 성립한다.
- 한 표가 두 분야에서 다른 역할을 하면, 그건 **DOM 표준 2개**로 갈릴 사안이다
  (DDS 04 §2 3층 계층 — `DOM-인사-인력` / `DOM-원가-단가`). **이미 있는 메커니즘이다.**
- 표준에 안 붙은 데이터셋은 §4 규칙으로 **직접 추론**하고 `source`·`confidence`를 남긴다.

> **왜 인스턴스가 아니라 표준에 붙이나**: 같은 표준의 인스턴스는 전부 같은 일을 한다.
> 인스턴스마다 붙이면 같은 판단을 N번 하고 N번 어긋난다. 인스턴스별로 갈리는 것
> (정본/부본·부분집합)은 `dataset_canon`(§2)이 이미 담당한다.

## 4. 판정 — 싼 것부터, 그리고 관계가 역할을 보정한다

| 단 | 방법 | 확신도 |
|---|---|---|
| **V1 구조 규칙** | §3 판정 신호 (컬럼 role 구성·행수·시간축 유무·증가율) | 0.6~0.9 |
| **V2 값 대조** | 다른 표의 `category` 값 집합과 일치 → `code` 확정 | 0.9 |
| **V3 관계 신호** | **fan-in 높음(많이 참조됨) → master·code** / **fan-out 높음 → transaction·bridge** | 0.7~0.95 |
| **V4 사람** | 표준 승인 시 지정 | 1.0 (덮이지 않음) |

**V3가 §20 관계 그래프와 맞물리는 지점이다** — 그리고 **순환에 주의해야 한다**:

```
역할을 알면 → 조인 방향·참조 기본값이 정해진다 (§5)
관계가 쌓이면 → fan-in/out 으로 역할을 역추론한다 (V3)
```

**순환을 끊는 규칙**: 초기엔 **V1·V2(구조·값)만** 쓴다. V3는 해당 표준에 **엣지 5개 이상**이
쌓인 뒤에만 보정으로 개입하고, **V1과 충돌하면 확정하지 않고 사람에게 묻는다.**
추론이 추론을 근거로 확신을 올리는 것을 막는다.

## 5. 역할이 실제로 바꾸는 것 — 이게 없으면 분류는 장식이다

역할을 매기는 이유는 **동작이 달라지기 때문**이다. 달라지는 것이 없으면 태그일 뿐이다.

| # | 역할이 결정하는 것 | 규칙 |
|---|---|---|
| **B1 조인 방향** | `master`·`code` 는 항상 **1쪽(lookup)**, `transaction` 은 **N쪽** | 역방향 fk 후보는 **의심 링크**로 강등 |
| **B2 집계 대상** | 집계는 `transaction`·`plan` 에만. **`code`·`bridge`·`master` 를 세면 중복 계수** | 위젯 생성 시 기본 제외 |
| **B3 기본 참조 제안** (§20 Q2) | 새 작업에 그 분야의 `master`+`code` 를 **기본 후보로 항상 포함** | 사용 이력이 없어도 제안 가능 — **콜드 스타트 해소** |
| **B4 시점 처리** | `snapshot` 은 기본 **최신 1건**, 시계열 질의에서만 전체 | `dataset_canon` 의 `older_version` 규칙과 정합 |
| **B5 실적 대비** | `plan` ↔ `transaction` 이 같은 표준이면 **계획 대비 실적** 조인이 기본 제안 | 이 프로젝트의 진척률 계산이 정확히 이 형태다 |
| **B6 변경 감시** | `master`·`code` 가 갑자기 크게 바뀌면 **경고** (기준정보는 잘 안 변한다) | 업로드 사고 조기 감지 — IA 252→213 덮어쓰기 사고가 실례 |

> **B3가 가장 값이 크다.** §20에서 사용 이력(`used_in`)이 콜드 스타트에 약하다고 했는데,
> **역할이 그 구멍을 메운다** — 이력이 0건이어도 "이 분야의 기준정보·코드표"는 항상 제안할 수 있다.
> **B6는 공짜 부수효과다** — 실제로 겪은 사고(`TODO.md` 2026-09-11 IA 전량 교체)를 이 규칙 하나가 잡는다.

## 6. 데이터 모델 — 컬럼 2개

**신규 테이블 없음.**

| 대상 | 추가 | 용도 |
|---|---|---|
| `standard_dataset` | `data_role VARCHAR(20)` | §3 6종 + unknown |
| `standard_dataset` | `role_source VARCHAR(10)` · `role_confidence DOUBLE` | 판정 출처(rule/stat/graph/human)와 확신도 |
| `dataset` | *(추가 없음)* | `std_id` 로 상속. 미바인딩 건만 §4 직접 추론 → `dataset_facet`(axis=`data_role`)에 기록 |

`dataset_facet` 재사용이 가능한 이유: 그 표는 `axis + value + target_type + confidence + source + evidence`
구조라 **축 하나 추가에 DDL 변경이 없다**(DDS ADR D2가 노린 바로 그 이점).

**API**: `GET /api/dds/standards/{stdId}` 응답에 `dataRole` 추가 ·
`PUT /api/dds/standards/{stdId}/role` (사람 지정, V4) · `POST /api/dds/roles/infer` (V1~V3 일괄).

## 8. ADR

| # | 결정 | 대안 | 왜 |
|---|---|---|---|
| R-A1 | 역할은 **표준**에 붙고 데이터셋은 상속 | 데이터셋마다 지정 | 같은 표준 인스턴스는 같은 일을 한다. N번 판단하면 N번 어긋난다 |
| R-A2 | 분야별 차이는 **DOM 표준 분리**로 | (분야, 데이터셋) 쌍 테이블 | DDS 3층 계층이 이미 그 용도다. 새 축을 만들면 계층이 둘로 갈린다 |
| R-A3 | **6종으로 닫는다** | 자유 분류 | 값이 늘면 §5 동작 규칙 6개가 전부 불완전해진다 |
| R-A4 | V3(관계 기반 추론)는 **엣지 5개 이상 + V1 불충돌** 조건부 | 즉시 반영 | 역할↔관계 순환 참조 차단. 추론이 추론을 근거로 확신을 올리면 안 된다 |
| R-A5 | 이름 충돌은 **섞어 쓰지 않고 rename 으로 해소** | 문맥으로 구분 | 같은 단어가 두 뜻이면 반드시 사고가 난다(T115 SSI 원천 단일성) |
