## 1. 목표

- 공개돼도 되는 정보와 그렇지 않은 정보를 **구분해서 저장**한다.
- 공개되면 안 되는 개인정보는 **RSA 공개키로 암호화**해 두고, **개인키를 가진 곳에서만** 원문을 복원한다.
- DB 파일·백업·덤프·git 저장소·로그가 유출돼도 **개인키가 없으면 원문이 나오지 않는** 상태를 만든다.

  (`기획` 99건 · `미정` · `전체` · `고객사`).
- 이름이 **자유 텍스트**에도 있다 — 결함 내용·조치, IA 비고, WBS 작업명·경로, 업로드 시트의 개인정보 아닌 칸,

- 기본 설정(`wbs.source: excel`)은 WBS 를 **엑셀 파일에서 직접** 읽는다 — DB 만 바꾸면 화면엔 원문이 나간다.

→ 지금 있는 것은 **일반 개인정보(성명)** 뿐이다. 법이 암호화를 **의무**로 정한 고유식별정보(주민등록번호 등)는
없다. 그래도 요구대로 성명까지 보호 대상으로 두고, 장차 들어올 전화·이메일·고유식별정보도 같은 틀로 받는다.

## 3. 핵심 결정 — 컬럼 암호화가 아니라 **가명처리 + 암호화 금고**

`owner` 를 그대로 암호화하면 안 된다. 이 값은 12개 파일에서 **집계(GROUP BY)·필터·검색·뷰**의 키로 쓰인다.
암호문은 매번 달라서(무작위 IV) 같은 사람끼리 묶이지 않고, 기존 기능이 전부 깨진다.

그래서 개인정보보호법의 **가명처리(§28-2)** 구조를 따른다:

```
  업무 테이블 (공개 가능)                     금고 pii_vault (공개 불가 원문은 암호문으로만)
  ┌──────────────────────────┐              ┌───────────────────────────────────────────────┐
  │ wbs_task.owner = PII-3fa2c1d9e0b1 │ ──→ │ token  PII-3fa2c1d9e0b1                         │
  │ defect.owner   = PII-3fa2c1d9e0b1 │      │ kind   person_name                             │
  │ dataset_row {"담당자":"PII-…"}   │      │ mask   김*수            ← 공개 가능 (표시용)      │
  └──────────────────────────┘              │ enc    v1:<RSA-OAEP(AES키)>:<IV>:<AES-GCM(원문)> │
     같은 사람 = 같은 토큰                    └───────────────────────────────────────────────┘
     → 집계·필터 그대로 동작                      원문은 개인키로만 복원
```

- **토큰**(`PII-` + 12자리 hex)은 `HMAC-SHA256(색인키, 종류:정규화값)` 이다. 같은 사람은 항상 같은 토큰이라
  기존 집계·필터가 코드 변경 없이 동작한다.
- **원문**은 금고에 **봉투 암호화**로만 있다 — 값마다 새 AES-256 키로 AES-GCM 암호화하고, 그 AES 키를
  RSA-3072 **공개키**(OAEP-SHA256)로 감싼다. RSA 로 원문을 직접 암호화하지 않는 이유: RSA 는 한 번에 수백
  바이트밖에 못 싸고 느리다. 표준 방식(봉투 암호화)이다.

## 4. 키 3종 — 역할이 다르다

| 키 | 누가 갖나 | 할 수 있는 것 | 유출되면 |
|---|---|---|---|
| **공개키** (RSA-3072) | 저장소에 커밋 — `backend/src/main/resources/pii/pii_public.pem` | 암호화만 | 문제 없음 (공개가 전제) |
| **색인키** (HMAC 32바이트) | 서버 `backend/.env` 의 `PM_PII_INDEX_KEY` (git 제외) | 이름 → 토큰 계산 (적재·검색) | 이름 후보를 넣어 토큰을 맞춰 볼 수 있다 → **교체 필요** |
| **개인키** (RSA-3072) | 저장소 **밖** 파일 — `PM_PII_PRIVATE_KEY` 가 경로를 가리킴 | 원문 복원 | 원문 전부 노출 → **즉시 교체 + 재암호화** |

색인키를 공개키처럼 공개할 수 없는 이유: 성명은 후보가 적다. 색인키가 있으면 "홍길동"을 넣어 토큰을
계산해 보는 것만으로 누가 누구인지 알 수 있다.

## 5. 데이터 분류 4등급

| 등급 | 뜻 | 예 | 저장 | 화면 |
|---|---|---|---|---|
| **P0 공개** | 개인 식별 불가 | 화면ID·진척률·상태·일정 | 평문 | 그대로 |
| **P1 가명** | 토큰·마스킹 값 | `PII-…`, `김*수` | 평문 | 그대로 |
| **P2 개인정보** | 특정 개인을 알아볼 수 있음 | 성명·전화·이메일·사번 | **토큰 + 금고 암호문** | 마스킹, 복원 허용 시 원문 |
| **P3 민감·고유식별** | 법이 암호화를 의무로 정함 | 주민번호·여권·운전면허·외국인등록번호·계좌·비밀번호 | **적재 금지가 원칙.** 불가피하면 금고 암호문만(토큰 검색 금지) · 비밀번호는 일방향 해시 | 항상 마스킹 |

분류 정본은 코드 한 곳이다 — `PiiRegistry` (컬럼 목록 + 업로드 시트 헤더 패턴).

## 6. 흐름

**적재**(엑셀 가져오기·결함 등록/수정·데이터셋 업로드): 분류가 P2 인 값 → `PiiVault.tokenize()` →
금고에 없으면 암호문·마스크를 저장 → 업무 테이블에는 토큰만 쓴다. 이미 토큰인 값은 건너뛴다(멱등).

**조회**: 서비스는 토큰을 그대로 반환한다. 응답이 나가기 직전 **한 곳**(`PiiResponseAdvice`)에서 JSON 안의
토큰을 표시값으로 바꾼다.
- 기본: `김*수#3fa2c1` (마스크 + 토큰 앞 6자리 — 마스크가 같은 두 사람을 구분)
- `pm.pii.reveal=true` **이고** 개인키가 로드됐을 때만 원문

**수정 폼 되돌림**: 화면이 받은 `김*수#3fa2c1` 을 그대로 다시 보내도 같은 토큰으로 되돌린다.

**복합값**: 성명 칸은 구분자(`,` `/` 공백 등)로 나눠 **사람 조각(한글 2~4자, 역할어 아님)만** 토큰으로 바꾼다 —
`고객사,홍길동` → `고객사,PII-…`. 역할어는 평문(P0)이다 — 마스킹하면 화면만 망가진다. 사람 조각도 역할어도 아닌
모르는 형식은 **값 전체를 토큰**으로(보호 쪽으로 기운다).

**자유 텍스트**: 금고에 있는 사람만 찾아 바꾼다(`PiiVault.scrub`). 한글 3~4자 조각마다 색인키로 토큰을 계산해
금고에 있으면 치환 — 개인키 없이 동작한다. 칸 전체를 암호화하지 않는 이유는 검색·표시가 깨지기 때문이다.
응답 치환은 문자열 **중간의** 토큰도 바꾸므로 `홍*동#3fa2c1님 확인 후 재배포` 로 보인다.
**2자 이름은 자유 텍스트에서 찾지 않는다** — 일반 단어와 겹친다(수용 제약, 담당자 칸의 2자 이름은 토큰화된다).

**엑셀 직접 조회**(`wbs.source: excel`): `ExcelWbsRepository` 가 읽는 즉시 같은 처리를 한다(요청 단위 메모로
같은 값은 한 번만 — 실측 `/api/wbs` 304ms).

**검색**: 이름으로 검색하면 같은 방식으로 토큰을 계산해 **정확히 일치**로 찾는다. 이름 일부로 찾는
부분 검색은 원리적으로 불가능하다(수용한 제약).

## 7. 기존 데이터 전환

`POST /api/admin/pii/migrate` (쓰기 API → API 키 필요). 안전장치 3개:
1. **개인키가 로드돼 있어야** 실행된다. 개인키 없이 전환하면 원문을 영영 못 되찾는다.
2. 실행 전 **왕복 시험**(암호화 → 복호화 → 원문 일치)이 통과해야 한다.
3. 멱등 — 이미 토큰인 값은 건너뛴다. 여러 번 실행해도 결과가 같다.

전환 순서: 정형 컬럼 → 데이터셋 1차(시트에만 있는 사람까지 금고에) → 자유 텍스트 → 데이터셋 2차.
본문 속 이름은 금고에 있는 사람만 찾으므로 순서가 결과를 바꾼다.

H2 는 삭제한 데이터를 파일에 한동안 남긴다 → 전환 후 `SHUTDOWN COMPACT` 로 파일을 다시 써야 평문이 사라진다.
전환 전 백업은 평문을 담고 있으므로 **검증 후 폐기**한다(지침 G-9).

### 7.1 운영 DB 복사본 실측 (2026-09-24)

| 항목 | 결과 |
|---|---|
| 전환 | 정형 757칸 · 자유 텍스트 40칸 · 시트 552행 → 금고 22명 · 남은 변환 대상 0 · 재실행 변경 0(멱등) |
| 응답 | `/api/defects`·`/api/ia/scope`·`/api/wbs` 토큰 노출 0 · 평문 담당자 = 역할어 `고객사` 뿐 |
| 파일 바이트 (H2 내부 인코딩으로 검색, `SHUTDOWN COMPACT` 후) | 3자 이상 이름 **15 → 0** · 2자 조각 3 잔존(위 수용 제약) · 2.2MB → 0.3MB |

첫 전환 시도는 **원자적으로 실패**했다 — HTML 가이드 시트의 "헤더"가 `<li … name=…>` 조각이라 성명으로 오분류돼
443자 값이 금고에 들어가려 했다. 트랜잭션이라 아무것도 바뀌지 않았고, 40자 초과·`<` 포함 헤더를 분류에서
제외하고 긴 값의 마스크를 제한해 해결했다.

## 9. 대안 비교

| 방식 | 집계·검색 | 유출 시 | 판단 |
|---|---|---|---|
| 컬럼 직접 암호화 | **전부 깨짐** | 안전 | 기존 기능 12곳 재작성 — 기각 |
| 결정적 암호화(같은 값 = 같은 암호문) | 동작 | 빈도 분석에 약함, RSA 로는 불가 | 기각 |
| DB 전체 암호화(TDE) | 동작 | 파일만 보호, 서버 권한자는 다 봄 | 공개/비공개 **구분**이 안 됨 — 기각 |
| **가명 토큰 + 암호화 금고** | 동작 | 개인키 없으면 원문 없음 | **채택** |
