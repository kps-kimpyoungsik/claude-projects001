# 05. 어휘 사전 설계 — 도메인 전문 용어의 흡수·보존·진화

> **어휘 사전은 선택이 아니라 필수다.** 사전이 없으면 분류기는 컬럼명을 못 읽고, 바인딩은
> 동의어를 못 잇고, 질의는 사용자가 쓴 업무 용어를 못 알아듣는다. 6축·표준·질의 셋 다
> 사전 위에 서 있다.
>
> 이 문서가 답하는 세 가지: **어디서 어디까지 가져올 것인가(경계)** ·
> **가져오면서 의미를 어떻게 안 잃을 것인가(보존)** · **쓰면서 어떻게 바뀔 것인가(진화)**.

---

## 1. 사전이 없으면 무슨 일이 생기는가 (실측)

| 상황 | 사전 없음 | 사전 있음 |
|---|---|---|
| `담당자` / `PM` / `책임자` | 서로 다른 3개 컬럼 | 전부 `person_name` 에 바인딩 |
| `기획 피드백` | 그냥 문자열 | `plan_status` 코드집합의 한 값, 결함 자동등록 트리거라는 의도까지 보존 |
| 사용자가 "여신 화면 결함" 검색 | 매칭 실패 | `여신`=area 어휘, `화면`=STD-SCREEN, `결함`=domain → 패싯 3개로 해석 |
| `DF-2026-001` | 무의미한 문자열 | `defect_id` 형식 규칙, 채번 주체가 시스템이라는 사실까지 |

## 2. 사전의 구조 — 3계층 × 4종

### 2.1 3계층 (표준 데이터셋과 같은 축)

| 계층 | 범위 | 승인 | 예 |
|---|---|---|---|
| **표준 어휘** | 전사 공통 | 필요(07 §4) | `담당자`, `진척률`, `결함` |
| **도메인 어휘** | 특정 업무 도메인 | 도메인 오너 | `여신등급`, `심사단계`, `한도소진율` |
| **로컬 어휘** | 한 데이터셋 범위 | 불필요 | 그 표에만 나오는 약어 |

로컬에서 자주 쓰이면 도메인으로, 도메인 여럿에서 쓰이면 표준으로 **승격 제안**된다(§5).

### 2.2 4종 용어

| 종류 | 무엇 | 예 |
|---|---|---|
| **개념어(concept)** | 업무 대상·행위 | 결함, 화면, 작업, 이슈 |
| **속성어(attribute)** | 개념의 성질 = 표준 필드와 짝 | 담당자, 등록일, 심각도 |
| **코드값(code)** | 열거된 값 집합 | 상태={신규,진행중,완료,보류} |
| **단위·형식(unit/format)** | 수치의 뜻, 식별자 형식 | `%`, `원`, `DF-YYYY-NNN` |

**코드값이 제일 중요하고 제일 자주 빠진다.** `상태`가 무엇인지 알아도 그 값이 몇 종인지
모르면 집계가 안 된다. 코드집합은 값 목록 + **각 값의 의미**를 함께 가진다.

## 3. 흡수 경계 — 어디서 어디까지

### 3.1 어디서 (출처 4종, 신뢰도 순)

| 순위 | 출처 | 신뢰도 | 흡수 방법 |
|---|---|---|---|
| 1 | **사람이 직접 등록** | 최고 | 그대로. 다른 어떤 것도 이걸 덮지 않는다 |
| 2 | **기존 DB 실측값** (`ia_screen.d1`, `defect.status` DISTINCT) | 높음 | 값 목록 자동 추출 → 코드집합 초안 |
| 3 | **업로드 문서**(엑셀 헤더·시트명·범례 행) | 중간 | 반복 출현 토큰만. 1회성 값 제외 |
| 4 | **외부 표준·규격 문서**(PDF 등) | 상황별 | Phase 4. 사람 검수 없이 approved 금지 |

### 3.2 어디까지 (IN / OUT 경계 — 이게 핵심)

**흡수한다(IN)** — 데이터의 *의미를 결정하는* 것만:

| 대상 | 판정 신호 |
|---|---|
| 반복 출현하는 헤더 토큰 | 2개 이상 데이터셋에 등장 |
| 고유값이 적은 컬럼의 값 집합 | distinct ≤ 20 (코드값 후보) |
| 식별자 패턴 | 정규 형식으로 표현 가능 (`DF-\d{4}-\d{3}`) |
| 단위 표기 | 값 끝의 `%`, `원`, `일`, `건` |
| 약어·머리글자 | 3자 이하 대문자/한글 조합이 반복 |

**흡수하지 않는다(OUT)** — 용어가 아닌 것:

| 제외 대상 | 이유 | 판정 |
|---|---|---|
| **개인정보** | 사람 이름·연락처·사번은 어휘가 아니라 **데이터**다 | `person` role 컬럼의 *값*은 흡수 금지(필드명만 흡수) |
| **비밀·키** | 유출 위험 | 패턴 차단 + 길이 |
| **1회성 값** | 한 번 나온 값은 어휘가 아니다 | 출현 1회 & 고유값 비율 높음 |
| **문장 전체** | 용어가 아니라 내용 | 길이 > 30자 또는 공백 3개 초과 |
| **숫자·날짜 그 자체** | 값이지 용어가 아님 | number/date 타입 값 |
| **파일명·경로** | 메타지 업무 용어가 아님 | 확장자·구분자 패턴 |

> **경계를 넘은 흡수가 가장 위험하다** — 개인정보가 사전에 들어가면 그때부터 사전은
> 공유·검색·백업 대상이 아니라 **관리 대상 자산**이 된다. IN 목록은 좁게 유지한다.

### 3.3 흡수 기록 (어디서 왔는지 잃지 않는다)

```sql
CREATE TABLE vocab_source (
  source_id    VARCHAR(60) PRIMARY KEY,
  kind         VARCHAR(20) NOT NULL,      -- human | db | upload | external
  uri          VARCHAR(500),              -- 파일명·테이블명·URL
  scope_in     VARCHAR(500),              -- 이 출처에서 무엇을 가져오기로 했나
  scope_out    VARCHAR(500),              -- 무엇을 일부러 제외했나 (판단 근거 보존)
  absorbed_at  VARCHAR(20),
  term_count   INTEGER
);
```

`scope_out` 을 적는 이유: 6개월 뒤 "왜 이 용어는 사전에 없지?"에 답하기 위해서다.
**제외도 결정이므로 기록한다.**

## 4. 의미 보존 — 흡수하면서 무엇을 잃지 않을 것인가

### 4.1 용어 1건의 필수 3종

```sql
CREATE TABLE vocab_term (
  term_id      VARCHAR(60) PRIMARY KEY,
  level        VARCHAR(10) NOT NULL,      -- STD | DOM | LOCAL
  kind         VARCHAR(20) NOT NULL,      -- concept | attribute | code | unit
  term         VARCHAR(200) NOT NULL,     -- 대표 표기
  domain       VARCHAR(100),
  definition   VARCHAR(1000) NOT NULL,    -- ① 무엇인가       (필수)
  intent       VARCHAR(500),              -- ② 왜 쓰는가       (필수 권장)
  source_id    VARCHAR(60) NOT NULL,      -- ③ 어디서 왔나     (필수)
  synonyms     VARCHAR(1000),             -- 이 용어로 취급할 다른 표기들
  related      VARCHAR(500),              -- 함께 보는 용어 (term_id 쉼표)
  code_values  VARCHAR(4000),             -- kind=code 일 때 {"값":"의미"} JSON
  format_rule  VARCHAR(200),              -- kind=unit/format 일 때 정규식·단위
  axis         VARCHAR(20),               -- 6축 중 어디에 쓰이는 어휘인가
  std_field    VARCHAR(160),              -- 표준 필드와 짝이면 "std_id.field_key"
  status       VARCHAR(20) NOT NULL,      -- draft | review | approved | deprecated
  version      INTEGER DEFAULT 1,
  confidence   DOUBLE PRECISION,
  usage_count  INTEGER DEFAULT 0,         -- 실제 매칭에 쓰인 횟수 (진화 근거)
  miss_count   INTEGER DEFAULT 0,         -- 매칭 실패 횟수 (개정 신호)
  created_at   VARCHAR(20),
  updated_at   VARCHAR(20)
);
CREATE INDEX idx_vocab_term ON vocab_term (term);
CREATE INDEX idx_vocab_axis ON vocab_term (axis, level);
```

**`definition`(무엇) · `intent`(왜) · `source_id`(어디서) 3종이 없으면 draft를 벗어나지 못한다.**
`intent` 를 필수에 가깝게 두는 이유: 사용자 요구의 핵심이 "의도 보존"이기 때문이다.
`상태` 의 정의는 "작업 진행 정도"지만, 의도는 "완료 집계의 기준이 되는 값"이다 —
의도를 잃으면 6개월 뒤 누군가 상태값을 하나 추가해 집계를 조용히 망가뜨린다.

### 4.2 병합해도 원본을 버리지 않는다

동의어 통합 시 `담당자`·`PM`·`책임자` 중 하나를 대표로 올리고 **나머지는 `synonyms` 에 남긴다.**
원 표기를 지우지 않는 이유:
- 원본 엑셀은 여전히 그 표기를 쓴다 → 재적재 시 다시 매칭돼야 한다
- 표기 자체가 출처의 맥락이다(어느 팀이 쓰는 말인지)

### 4.3 의미 충돌은 병합하지 않고 **분리**한다

같은 단어가 도메인마다 다른 뜻이면(`상태`가 결함에선 처리단계, 화면에선 개발단계)
**억지로 하나로 만들지 않는다.** `domain` 을 달리해 별도 term 으로 두고, `related` 로 잇는다.
억지 통합은 데이터를 조용히 뒤섞는다 — 사전이 할 수 있는 가장 큰 사고다.

## 5. 진화 — 쓰면서 바뀐다

> 사용자 요구: *"진행에 따라 데이터셋 학습 정보가 변형됩니다"*

### 5.1 진화 신호 4종 (자동 수집)

| 신호 | 수집 방법 | 의미 | 자동 조치 |
|---|---|---|---|
| **미매칭 토큰 누적** | 분류·바인딩 실패 시 그 토큰 기록 | 사전에 없는 용어 | 3회 이상 → LOCAL draft 자동 생성(등재 아님, 후보) |
| **코드값 확장** | 코드집합에 없는 값 출현 | 값이 늘었다 | 기록 + 표면화. **자동 추가 안 함**(집계 의미가 바뀌므로) |
| **사용 빈도** | `usage_count` | 이 용어가 실제로 쓰인다 | LOCAL→DOM, DOM→STD 승격 제안 |
| **매칭 실패율** | `miss_count / (usage+miss)` | 정의가 실제와 어긋난다 | 0.3 초과 → 개정 검토 대상 표면화 |

### 5.2 변경 이력 (되돌릴 수 있게)

```sql
CREATE TABLE vocab_history (
  term_id      VARCHAR(60) NOT NULL,
  version      INTEGER NOT NULL,
  change_kind  VARCHAR(20),               -- create | definition | synonym | code | promote | deprecate
  before_val   VARCHAR(2000),
  after_val    VARCHAR(2000),
  reason       VARCHAR(500) NOT NULL,     -- 왜 바꿨나 — 빈 값 불가
  decided_by   VARCHAR(50),               -- 사람 이름 또는 rule/stat/llm
  at           VARCHAR(20),
  PRIMARY KEY (term_id, version)
);
```

**정의 변경은 항상 새 버전이다.** 덮어쓰기 없음. 과거 데이터셋이 과거 정의로 해석된 사실이
남아야 "그때 그 집계가 왜 그 값이었나"에 답할 수 있다.

### 5.3 진화가 과거를 망가뜨리지 않게 — 3원칙

1. **추가는 자유, 변경은 승인** — 용어 신설은 draft 로 자유롭게. 기존 정의 변경은 승인(07).
2. **자동 승격 없음** — 빈도가 높다고 시스템이 STD 로 올리지 않는다. 제안만 한다.
3. **소급 재해석 없음** — 사전이 바뀌어도 이미 붙은 태그·바인딩을 자동으로 고치지 않는다.
   재분류는 명시적 실행(`POST /api/dds/reclassify`)이며, `source='human'` 은 그때도 보존된다.

## 6. 분류기·바인딩이 사전을 쓰는 방법

```
컬럼명 "PM"
  │
  ├─ ① 정확 일치        vocab_term.term = 'PM'          → 없음
  ├─ ② 동의어 일치      synonyms LIKE '%PM%'            → '담당자' 발견 (confidence 0.9)
  ├─ ③ 부분·정규화 일치  공백·괄호 제거 후 재시도          → -
  └─ ④ 실패            miss_count++ , 미매칭 토큰 기록   → 진화 신호(§5.1)

  결과: 컬럼 "PM" → vocab '담당자' → std_field 'STD-TASK.owner' → role 'person'
        한 번의 사전 조회가 6축 role, 표준 바인딩, 질의 어휘를 동시에 해결한다
```

**사전이 세 곳을 동시에 먹인다** — 이것이 사전을 별도 시스템이 아니라 DDS의 중심에 두는 이유다.

## 7. 설계 결정 (ADR)

| # | 결정 | 대안 | 이유 | 깨지는 조건 |
|---|---|---|---|---|
| V1 | `definition`+`intent`+`source` 3종 필수 | 용어와 동의어만 | 의도 없는 사전은 6개월 뒤 아무도 못 고친다(왜 그렇게 정했는지 모름) | 없음 — 작성 비용이 유일한 부담 |
| V2 | 개인정보 **값**은 흡수 금지(필드명만) | 전부 흡수 | 사전이 개인정보 저장소가 되면 성격이 완전히 달라진다 | 없음 |
| V3 | 의미 충돌은 **분리**(domain 분기) | 단일 표준어로 통합 | 억지 통합은 데이터를 조용히 뒤섞는다. 되돌리기 어렵다 | 도메인이 20개 넘어 term 폭증 시 상위 개념 도입 검토 |
| V4 | 코드값 자동 추가 **안 함** | 새 값 자동 등록 | 코드집합이 늘면 집계 의미가 바뀐다. 조용히 바뀌면 안 된다 | 없음 |
| V5 | 자동 승격 없음(제안만) | 빈도 임계 자동 승격 | 표준은 합의다. 빈도는 합의의 근거일 뿐 합의 자체가 아니다 | 없음 |
| V6 | 소급 재해석 없음 | 사전 변경 시 전체 재태깅 | 과거 집계 결과가 소리 없이 바뀐다 = 신뢰 붕괴 | 명시적 재분류는 언제든 가능하므로 손실 없음 |

## 8. 초기 사전 시드 (실측에서 — 손으로 안 쓴다)

| 종류 | 출처 | 예상 건수 |
|---|---|---|
| 속성어 | `wbs_task`·`ia_screen`·`defect` 컬럼명 63개 → 정규화·중복제거 | ~45 |
| 코드값 | `defect.status` · `ia_screen.status` · `plan_status` DISTINCT | 5집합 ~30값 |
| 영역 개념어 | `ia_screen.d1`·`d2` DISTINCT | ~20 |
| 분야 개념어 | 7종 고정(일정관리·개발·테스트·결함·인프라·인력·이슈) | 7 |
| 형식 | `DF-YYYY-NNN`, `DS-*`, `UP-*`, `WS-*` | 4 |

**전부 DB 질의 한 번으로 나온다.** 사람이 채우는 것은 `definition`·`intent` 뿐이며,
그것도 초안은 컬럼 주석·README 에서 끌어올 수 있다.

**공통 사전과 도메인 사전이 실제로 갈린다** — 전사 공통 24건, `화면분류` 도메인 57건,
한 표 범위 31건. 계층 필터로 각각을 따로 관리한다.

**DoD 달성** — 실제 헤더 40개 중 40개(100%)가 사전으로 해석된다(목표 80%).

### 설계에서 바꾼 것 하나 (§3.2 헤더 조건)

§3.2 의 "반복 출현하는 헤더 토큰 = 2개 이상 데이터셋에 등장"을 **헤더에는 걸지 않았다.**
실측 6개 데이터셋은 서로 다른 시트라 겹치는 헤더가 9개뿐이었고, 조건을 그대로 걸면
`담당자`·`진행상태`·`우선순위` 같은 핵심 속성어가 통째로 빠져 해석률이 22% 에 그쳤다.

대신 **확신도로 구분**한다 — 여러 표에 걸친 헤더 0.6~0.9, 한 표에만 있는 헤더 0.4(둘 다 draft).
§8 이 애초에 "컬럼명 63개 → 속성어 ~45"를 기대하고 있었으므로 §8 쪽 의도를 따랐다.
**ADR V2(개인정보 값 흡수 금지)는 그대로다** — 헤더는 이름이지 값이 아니라 여기서 위험이 생기지 않는다.

### 공통 사전 관리 (§2.1 3계층 실장, 2026-09-14 보강)

| 계층 | 무엇이 들어가나 | 배정 근거 |
|---|---|---|
| **STD(공통)** | 분야·식별자 형식·코드집합 + **2개 이상 표에 나온 헤더** | 공통성 — 여러 표가 같은 말을 쓴다 |
| **DOM(도메인)** | 화면 분류에서 뽑은 영역 어휘 (`domain='화면분류'`) | 소속 도메인이 있어야 특정 사전이 성립한다 |
| **LOCAL(로컬)** | 한 표에만 있는 헤더, 미매칭 3회 누적 초안 | 그 표 범위 |

- **승격은 시스템이 하지 않는다**(ADR V5) — `GET /api/dds/vocab/promotions` 가 근거만 낸다:
  "표 N개에 같은 헤더로 존재" · "매칭에 N회 사용"(하한 5). 올리는 것은 화면의 `공통으로 올리기`
  버튼(= 사람의 PUT)이고, 그때 이력에 `promote` 로 남는다.
- **재시드가 계층을 올리지 않는다** — 이미 있는 용어는 `level` 을 건드리지 않는다
  (`VocabStore.exists()` 로 확인). 그래서 재실행이 조용한 자동 승격이 되지 않는다.
- **의미 충돌은 분리**(ADR V3) — 같은 표기라도 `domain` 이 다르면 별도 용어다. 화면 편집기에서
  `domain` 을 지정해 나눈다.

### 남은 것

- `ia_screen.status`(개발완료여부)·`plan_status`(기획검토상태) 코드집합 2건이 비어 있다.
  사전 문제가 아니라 **IA 데이터 자체가 비어 있기 때문**이다(`TODO.md` 2026-09-11 업로드 덮어쓰기 사고).
  `POST /api/unittest/import` 로 IA 를 복원한 뒤 시드를 재실행하면 채워진다.
- 코드값의 *각 값의 의미*는 전부 빈 문자열이다. 사람이 채우는 몫(P7 에서 지속).
- 사전 API 는 아직 무인증이다 — P0-3 과 같은 게이트에 걸린다(쓰기 API Key 미결정).
- 도메인이 `화면분류` 하나뿐이다. 실제 업무 도메인(여신·수신 등)은 P2 에서 표준 데이터셋을
  세우면서 같이 갈린다 — 지금 손으로 넣으면 P2 배정과 어긋난다.
- **계층 배정 규칙이 바뀌면 기존 자동 초안은 `schema.sql` 일회성 정리로 다시 쓴다.**
  "사람이 손댔는가"는 `version` 이 아니라 `vocab_history.decided_by='human'` 으로 판정한다 —
  재시드만으로도 version 은 오르기 때문에 version 으로 보면 자동 초안을 사람 작업으로 오인한다(실측).

## 10. 원천 단일성 — 수집 시점 3분류 (2026-09-14, AEGIS T115 SSI 적용)

> **원천 정보 1개 = 등재 1건.** 정본 헌법: `D:\aegis\core\constitution\dev_rules\SOURCE-SINGULARITY-INGEST.md`

### 10.1 왜 §3.2 만으로 부족했나 (실측)

§3.2 의 흡수 경계는 **"이걸 넣어도 되는가"** 만 본다. 넣어도 되는 것들 사이의 **관계**는 보지
않는다. 그 결과 112건 수집 결과가 이랬다:

| 실측 | 무엇이 문제인가 |
|---|---|
| `결함상태`·`진행상태`·`처리상태` | 원천 `상태` 없이 파생만 3벌 — 이을 축이 없다 |
| `수행 담당자`·`현업담당자` | 원천 `담당자` 없음 |
| `시작일`·`완료일`·`종료일`·`계획완료일`·`검토시작일` | 원천 `일` 없음 |
| `완료/처리중/대기`·`접수상태(개선,검토)` | 값이 속성어로 등재 — 집계 단위 오염 |

**표기 단위로 수집했기 때문**이다. 경계는 지켰지만 원천은 보지 않았다.

### 10.2 3분류 — `Ingest.classify()`

| 분류 | 판정 | 조치 |
|---|---|---|
| **VALUE** | 구분자(`/`·`,`)로 나뉜 배타 항목 2개 이상 | 속성어 아님 → 그 표기의 **코드집합**으로 |
| **DERIVED** | 앞에서 수식어 하나를 떼면 축이 남는다 | 원천을 먼저 세우고(`ensureSource`) `related` 로 연결 |
| **SOURCE** | 위 둘 다 아님 | 1건 등재 |

**수식어는 맨 앞에서 한 개만 뗀다** — `계획완료일` → `계획` + `완료일`(`계획일` 아님).
뒤에서 떼거나 한 번에 원천까지 내려가면 중간 단계(`완료일`)가 사라져 계보가 끊긴다.

### 10.3 적용 결과 (운영 DB 재시드)

```
[SSI] 원천 25 | 파생 13(원천 연결) | 값 2(코드집합) | 중복 후보 4묶음 → 표면화 | 자동 병합 0
```

- **원천이 실제로 섰다**: `상태`·`내용`·`일`·`날짜`·`여부` 가 등재되고 파생 13건이 이를 가리킨다
  (`검토시작일`→`시작일`→`일` 처럼 계보가 이어진다)
- **값이 분리됐다**: `완료/처리중/대기` → 코드집합 3값, `접수상태(개선,검토)` → 코드집합 2값.
  속성어 수가 40 → 38 로 줄고 코드집합 2건이 늘었다
- **자동 병합 0**: `진행상태`·`처리상태` 는 같은 원천을 가리키지만 **합치지 않았다**.
  뜻이 같은지는 사람만 안다 — 화면 `중복 후보` 탭에 4묶음이 판정 대기로 뜬다

### 10.4 남은 판단 (사람 몫)

| 묶음 | 물어야 할 것 |
|---|---|
| `진행상태` · `처리상태` | 같은 것인가? 같으면 동의어 흡수, 다르면 원천 `상태` 아래 파생 유지 |
| `수행 담당자` · `현업담당자` | 역할이 다르면 둘 다 파생으로 유지가 맞다 |
| `요청내용` · `확인내용` | 시점이 다른 별개 필드로 보인다 — 유지 쪽 |
| `시작일` · `완료일` · `종료일` | `완료일`·`종료일` 이 같은 것인지가 쟁점 |

**시스템은 여기까지만 한다.** 합치는 순간 과거 집계가 조용히 바뀌므로, 판정은 사람이 한다.
