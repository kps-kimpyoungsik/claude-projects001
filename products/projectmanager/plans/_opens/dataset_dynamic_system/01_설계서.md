# 01. 설계서 — 데이터셋 동적 생성·관리 시스템 (DDS, Dynamic Dataset System)

> 한 줄: **적재된 표에 6축 의미를 붙이고, 그 의미를 필터로 쓰는 "저장된 질의"를 데이터셋으로 발행한다.**

---

## 1. 현행 실측 (무엇이 이미 있는가)

| 구성 | 현행 | 파일 |
|---|---|---|
| 인제스트 | 엑셀 시트마다 헤더 행 자동 탐지 → 표 적재 | `DatasetIngestService.java` |
| 타입 추론 | number / date / category / text 4종 (비율 0.7 임계) | `ColumnProfiler.java` |
| 저장 | `dataset` · `dataset_column` · `dataset_row(payload JSON)` | `schema.sql` |
| 발행 | `dashboard` + `dashboard_widget` → LNB 메뉴 자동 생성 | `DashboardService.java` |
| 화면 | `데이터 > 데이터셋`, `데이터 > 대시보드` | `Shell.jsx` GROUPS |

**있는 것**: 표를 받아 저장하고 차트로 그리는 것까지.
**없는 것**: 이 표가 **무엇에 관한 것인지**(의미), 표들끼리 **어떻게 이어지는지**(관계),
그래서 **"OO에 관한 데이터 뽑아줘"에 답할 수 있는 경로**.
→ 본 설계는 **기존 3형제를 바꾸지 않고 그 위에 의미 계층을 얹는다.**

---

## 2. 목표 아키텍처 — 5계층

```
  L4  발행(Serve)      dataset_view = 저장된 질의  →  GET /api/dds/views/{id}/data
                       - 요청 시 SQL 조립. materialize=true 면 스냅샷으로 고정 발행
                       - 기본 대상은 primary + variant (중복 없는 답), scope=all 로 확장
  ---------------------------------------------------------------------------
  L3  의미부여(Enrich)  ① 어휘 매칭    (05 문서)  →  vocab_term
                       ② 표준 바인딩  (04 문서)  →  dataset_binding · dataset.std_id
                       ③ 6축 분류                →  dataset_facet
                       ④ CQG 자격평가 (06 §2)    →  dataset_qualification
                          REJECTED 면 여기서 종료 — 아래 계산을 돌리지 않는다
                       ⑤ PSR 주/부판정(06 §3)    →  dataset_role
                       ⑥ 관계·주제              →  dataset_link · topic
                       - 3계층 에스컬레이션(규칙 → 통계/임베딩 → LLM), 출처·확신도 기록
  ---------------------------------------------------------------------------
  L2  정제(Refine)      정규화 · 결측 · 중복 · 키 후보 탐지 → dataset_quality
                       - 날짜/숫자/코드 표기 통일. 원본 payload 보존, 정규값은 별도
  ---------------------------------------------------------------------------
  L1  구조화(Structure) 헤더 탐지 · 타입 추론      →  dataset / dataset_column / dataset_row
                       - 현행 그대로. 변경 없음
  ---------------------------------------------------------------------------
  L0  수집(Ingest)      업로드 창구 1개(POST /api/uploads) + 어댑터
                       - xlsx(현행) / csv / pdf·docx(Phase 4, 레이아웃 파서 어댑터)

  ※ L3 옆에 계층축이 하나 더 있다 — 데이터셋은 표준(STD) / 도메인(DOM) / 사용자(USR)
     3층 중 하나에 속한다. 04 문서 §2 참조. 이 축은 "무슨 데이터인가"가 아니라
     "얼마나 공용인가"를 가른다.
```

원칙: **아래 계층은 위 계층을 모른다.** L1까지는 지금 코드 그대로 돌고, L3가 없어도 시스템은 동작한다
(의미가 비어 있을 뿐). 즉 **증분 도입이 가능한 설계**다.

## 3. 6축 의미 모델 (핵심)

요청 원문의 "분야·영역·관계·의미·맥락·주제"를 그대로 축으로 고정한다. 축은 **6개로 닫는다** — 축이 늘면
질의 UI와 분류기가 동시에 무너진다. 축 안의 **값(어휘)** 은 자유롭게 늘어난다.

| # | 축 | 코드 | 붙는 대상 | 값 예시 | 산출 계층 |
|---|---|---|---|---|---|
| 1 | **분야** | `domain` | 데이터셋 | 일정관리 / 개발 / 테스트 / 결함 / 인프라 / 인력 / 이슈 | T1 규칙 |
| 2 | **영역** | `area` | 데이터셋·행 | 자금관리 / 여신 / 공통 / 대외연계 … (시스템·모듈 단위) | T1 규칙 + T2 값매칭 |
| 3 | **의미** | `role` | **컬럼** | id / time / status / measure / person / org / text / ref | T1 규칙 + T2 통계 |
| 4 | **맥락** | `context` | 데이터셋·배치 | 기준일=2026-08-31 / 출처=엑셀업로드 / 배치=UP-… / 버전 | T1 (이미 `upload_batch`에 있음) |
| 5 | **주제** | `topic` | 데이터셋·행(텍스트) | "로그인 화면 결함" / "이관 일정 지연" | T2 군집 + T3 라벨 |
| 6 | **관계** | `link` | 데이터셋↔데이터셋, 컬럼↔컬럼 | fk / same_entity / derived_from / time_aligned | T2 값겹침 + T3 검증 |

### 3.1 축별 판정 근거 (추정 금지 — 무엇을 보고 정하는가)

- **분야(domain)**: 컬럼명 시그니처 사전. 예) `{결함ID, 결함유형, 심각도}` ⊂ 컬럼명 → `결함`.
  `일치 컬럼 수 / 사전 컬럼 수` = 확신도. 0.6 미만이면 T2로 내린다.
- **영역(area)**: 값 도메인 매칭. 기준 어휘는 **이미 DB에 있는 것**을 쓴다 —
  `ia_screen.d1/d2`(화면 계층), `wbs_task.big/mid`(WBS 대분류). 새 사전을 만들지 않는다.
- **의미(role)**: `ColumnProfiler`를 확장한다. 현행 4타입은 **물리 타입**이고 role은 **업무 의미**다.
  판정 규칙:
  - 고유값 = 행수 ∧ 결측 0 → `id`
  - date 타입 → `time`
  - category ∧ 고유값 ≤ 10 ∧ 컬럼명에 상태어(상태/여부/구분) → `status`
  - number ∧ 합계가 유의 → `measure`
  - 다른 데이터셋의 `id` 컬럼과 값 겹침 ≥ 0.8 → `ref`
  - 컬럼명에 담당/작성/PM 등 → `person`, 그 외 text → `text`
- **맥락(context)**: 신규 추론 없음. `upload_batch`(파일명·업로드시각) + 데이터셋 내 최대 날짜값 = 기준일.
- **주제(topic)**: 텍스트 컬럼(role=text) 값을 임베딩 → 군집 → 대표어. 라벨만 LLM.
  **데이터셋 단위 주제**는 `이름 + 컬럼명 + 상위 카테고리 값`을 한 문서로 보고 같은 파이프라인에 태운다.
- **관계(link)**: 컬럼 값 집합의 **Jaccard 유사도**로 후보 생성(≥ 0.3). 한쪽이 role=id면 `fk`,
  양쪽 다 id면 `same_entity`. 확신도 0.3~0.7 구간만 T3(LLM)로 "둘이 같은 것을 가리키는가" 확인.

### 3.2 3계층 에스컬레이션 (비용 통제)

```
T1 규칙/사전       비용 0,   지연 ~ms    → confidence >= 0.8 이면 확정. 아래 계층 호출 안 함
   | (미달분만)
T2 통계/임베딩      비용 0(로컬), ~수백ms → confidence >= 0.7 이면 확정
   | (미달분만)
T3 LLM(스키마 강제) 비용 有,  ~초        → JSON Schema 강제 + 검증 실패 시 1회 재시도 후 미분류
   |
미분류(unknown)     화면에 "분류 필요"로 노출 → 사람이 지정하면 source=human 으로 고정
```

- **human은 절대 덮이지 않는다.** 재분류 배치는 `source='human'` 행을 건드리지 않는다.
- T3는 **기본 OFF**. `dds.llm.enabled=false` 가 기본값이며, 켜도 대상은 "T2 미달분"뿐이다.

## 4. 데이터 모델 (추가 5개 — 기존 테이블 변경 0)

```sql
-- 4.1 의미 태그: 6축 중 domain/area/role/context/topic 을 한 표에 담는다(축이 늘어도 DDL 불변)
CREATE TABLE dataset_facet (
  facet_id    VARCHAR(60) PRIMARY KEY,   -- FC-yyyyMMdd-HHmmss-n
  axis        VARCHAR(20) NOT NULL,      -- domain | area | role | context | topic
  value       VARCHAR(200) NOT NULL,     -- 축의 값 (통제 어휘)
  target_type VARCHAR(20) NOT NULL,      -- dataset | column | row
  dataset_id  VARCHAR(60) NOT NULL,
  col_name    VARCHAR(200),              -- target_type=column 일 때
  row_no      INTEGER,                   -- target_type=row 일 때
  confidence  DOUBLE PRECISION,          -- 0.0 ~ 1.0
  source      VARCHAR(10),               -- rule | stat | embed | llm | human
  evidence    VARCHAR(1000),             -- 왜 그렇게 봤는지 (일치 컬럼 목록 / 군집ID / 프롬프트ID)
  created_at  VARCHAR(20),
  updated_at  VARCHAR(20)
);
CREATE INDEX idx_facet_lookup ON dataset_facet (axis, value);
CREATE INDEX idx_facet_target ON dataset_facet (dataset_id, target_type);

-- 4.2 관계축(6번). 방향이 있다: from -> to
CREATE TABLE dataset_link (
  link_id     VARCHAR(60) PRIMARY KEY,
  link_type   VARCHAR(20) NOT NULL,      -- fk | same_entity | derived_from | time_aligned
  from_ds     VARCHAR(60) NOT NULL,
  from_col    VARCHAR(200),
  to_ds       VARCHAR(60) NOT NULL,
  to_col      VARCHAR(200),
  overlap     DOUBLE PRECISION,          -- Jaccard 실측값 (근거 수치)
  confidence  DOUBLE PRECISION,
  source      VARCHAR(10),
  created_at  VARCHAR(20)
);
CREATE INDEX idx_link_from ON dataset_link (from_ds);

-- 4.3 동적 데이터셋 = 저장된 질의(시맨틱 레이어). 이것이 "동적 생성"의 실체다.
CREATE TABLE dataset_view (
  view_id     VARCHAR(60) PRIMARY KEY,   -- VW-yyyyMMdd-HHmmss-n
  name        VARCHAR(200),
  description VARCHAR(500),
  spec        VARCHAR(8000),             -- JSON: {facets, sources, join, select, filter, agg, sort, limit}
  materialized BOOLEAN DEFAULT FALSE,    -- true면 결과를 dataset 3형제로 고정 발행
  out_dataset_id VARCHAR(60),            -- materialize 시 생성된 데이터셋
  hit_count   INTEGER DEFAULT 0,         -- 활용도 — 안 쓰이는 뷰 정리 근거
  created_by  VARCHAR(50),
  created_at  VARCHAR(20),
  updated_at  VARCHAR(20)
);

-- 4.4 정제 결과(L2). 원본 payload는 건드리지 않고 품질 지표만 따로 둔다.
CREATE TABLE dataset_quality (
  dataset_id   VARCHAR(60) NOT NULL,
  col_name     VARCHAR(200) NOT NULL,
  null_ratio   DOUBLE PRECISION,
  dup_ratio    DOUBLE PRECISION,
  fmt_variants INTEGER,                  -- 같은 뜻 다른 표기 수 (예: 2026-08-31 / 26.8.31)
  norm_rule    VARCHAR(200),             -- 적용한 정규화 규칙 id
  checked_at   VARCHAR(20),
  PRIMARY KEY (dataset_id, col_name)
);

-- 4.5 통제 어휘(택소노미). 축의 값을 아무나 만들지 못하게 한다.
CREATE TABLE facet_vocab (
  axis     VARCHAR(20) NOT NULL,
  value    VARCHAR(200) NOT NULL,
  parent   VARCHAR(200),                 -- 계층(대분류 -> 소분류)
  synonyms VARCHAR(1000),                -- 쉼표 구분 — 규칙 매칭 사전으로 그대로 쓴다
  note     VARCHAR(500),
  PRIMARY KEY (axis, value)
);
```

**왜 태그를 한 표(`dataset_facet`)에 몰았나**: 축마다 테이블을 만들면 축이 늘 때마다 DDL·API·화면이
같이 늘어난다. 축은 6개로 닫혀 있고 조회 패턴이 동일(`axis + value`로 찾기)하므로 단일 표가 맞다.
관계(link)만 분리한 이유는 **양쪽 끝을 가진 유일한 축**이라 형태가 다르기 때문이다.

## 5. 동적 생성 흐름 (요청 → 데이터셋)

```
[요청]  "2026-08 이후 결함 분야 데이터 중 화면영역이 '여신'인 것"
   |
   +- (1) 질의 해석 : 화면의 패싯 선택 UI (기본)
   |                  또는 자연어 1줄 -> 패싯 매핑 (Phase 4, LLM, 실패 시 UI로 폴백)
   |                  spec = {facets:{domain:["결함"], area:["여신"]},
   |                          filter:[{col:"등록일", op:">=", v:"2026-08-01"}]}
   +- (2) 후보 축소 : dataset_facet 조회 -> 대상 dataset_id 목록
   +- (3) 조인 계획 : dataset_link 에서 대상들 사이 fk/same_entity 경로 탐색 (최대 2홉)
   +- (4) SQL 조립  : dataset_row.payload JSON 추출 + 필터 + 집계 (프로젝션 기본값은 role 기준)
   +- (5) 결과 반환 : 미리보기 200행 + 총건수 + 사용된 근거(어느 데이터셋 / 어느 링크)
   +- (6) 발행(선택): "데이터셋으로 저장" -> dataset 3형제에 새 DS 생성 + dashboard 자동 초안
                      -> LNB 메뉴에 바로 뜬다 (기존 대시보드 파이프라인 재사용)
```

**근거 반환이 필수다**: 결과만 주면 사용자가 검증할 수 없다. 응답에 항상
`sources: [{dataset_id, name, matched_facets, rows}]` 와 `links_used: [...]` 를 포함한다.

## 6. 설계 결정과 트레이드오프 (ADR 요약)

| # | 결정 | 대안 | 채택 이유 | 깨지는 조건 |
|---|---|---|---|---|
| D1 | 기존 `dataset` 3형제 유지, 의미 계층만 추가 | 저장 모델 재설계 | 현행 업로드·대시보드가 그대로 돈다. 회귀 위험 0 | `dataset_row.payload` VARCHAR(100000) 한계 초과 행 등장 시 |
| D2 | 태그 단일 표(`dataset_facet`) | 축별 테이블 6개 | 축이 닫혀 있고 조회 패턴 동일. DDL/API/화면 증식 차단 | 축이 7개 이상 필요해지면 재검토 |
| D3 | 동적 데이터셋 = 저장된 질의(뷰), 기본 비물질화 | 항상 물리 테이블 생성 | 원본 1벌 유지. 원본 갱신 시 뷰는 자동 최신 | 수만 행 조인 시 지연 → `materialized=true`로 개별 전환 |
| D4 | LLM 기본 OFF, T2 미달분만 | 전건 LLM 라벨링 | 컬럼명 규칙성이 높아 T1·T2로 대부분 판정. 비용·환각 회피 | 자유서술 문서가 주 입력이 되는 순간(Phase 4) 기본값 재검토 |
| D5 | 임베딩·군집은 백엔드 내부 계산 | 벡터 DB 도입 | 데이터셋 수십 개·수천 행 규모. 운영 컴포넌트 추가는 과함 | 데이터셋 1,000개 또는 행 100만 초과 시 pgvector로 이전 |
| D6 | 6축 값은 `facet_vocab` 통제 어휘로만 | 자유 태그 | 자유 태그는 동의어 난립으로 검색이 무너진다 | 신규 값 요청이 주당 20건 이상이면 승인 워크플로 필요 |

## 8. 보강 (2026-09-14) — 뼈대·사전·게이트 3축 추가

초판(2026-09-13)은 "적재된 표에 의미를 붙인다"까지였다. 여기에 **들어오는 것을 거르고, 표준 모양에
맞추고, 용어의 뜻을 지키는** 세 축이 더해졌다. 초판 내용은 그대로 유효하며, 아래는 그 위에 얹힌다.

### 8.1 추가된 3축과 문서

| 축 | 답하는 질문 | 문서 | 없으면 생기는 일 |
|---|---|---|---|
| **뼈대**(표준 데이터셋) | 이 표는 원래 어떤 모양이어야 하나 | **04** | 표 100개 = 구조 100개. 통합 질의 불가 |
| **사전**(어휘·온톨로지) | 이 용어는 무슨 뜻인가 | **05** | 분류·바인딩·질의 셋 다 동의어를 못 잇는다 |
| **게이트**(자격·주부·승인) | 이게 데이터셋 자격이 있나 / 정본인가 / 표준이 될 만한가 | **06** | 쓰레기가 진짜를 덮고, 중복 집계가 생긴다 |

### 8.2 6축 의미모델과의 관계 — 대체가 아니라 보강

초판 6축(분야·영역·의미·맥락·주제·관계)은 **그대로 유지**한다. 추가 3축은 6축을 **먹이고 걸러준다**:

```
   사전(05) ─── 용어를 준다 ──→ 6축 분류기 (분야·영역·의미 판정의 재료)
      │                              │
      └── 동의어를 준다 ──→ 표준 바인딩(04) ──→ 6축의 관계축에 "정답"을 준다
                                     │            (standard_relation > dataset_link)
                                     ▼
                              자격 게이트(06) ── 6축을 붙일 가치가 있는 것만 통과
```

**한 번의 사전 조회가 6축 role·표준 바인딩·질의 어휘를 동시에 해결한다**(05 §6) — 이것이
사전을 별도 시스템이 아니라 DDS 중심에 두는 이유다.

### 8.3 관계축의 이원화 (중요 — 혼동하면 설계가 무너진다)

관계는 이제 **두 층**이다.

| | `standard_relation` (04) | `dataset_link` (초판 §4.2) |
|---|---|---|
| 층 | 정의(type) — "결함은 화면에 달린다" | 인스턴스 — "이 표와 저 표는 값이 겹친다" |
| 출처 | 사람 정의, 승인 대상 | 자동 추론(Jaccard) |
| 우선순위 | **먼저 본다** | 정의가 없을 때만 |

**추론이 정의를 이기지 않는다.** 질의 계획기는 표준 관계를 먼저 조회하고, 없을 때만 추론 링크로
내려간다. 초판 §5 ③(조인 계획)의 절차가 이에 맞춰 갱신된다.

### 8.4 초판 ADR의 정정·보강

| 초판 결정 | 상태 | 보강 |
|---|---|---|
| D1 기존 3형제 유지 | **유지** | `dataset` 에 컬럼 3개만 추가(`std_id`·`bind_ratio`·`level`) — 여전히 기존 테이블 재설계 없음 |
| D2 태그 단일 표 | **유지** | 표준 정의는 별도 테이블(형태가 다름). 태그는 그대로 단일 표 |
| D3 뷰 기본 비물질화 | **유지** | 대상 선정에 `dataset_role` 필터가 추가됨(primary+variant 기본) |
| D4 LLM 기본 OFF | **유지** | 사전이 생기면서 T1(규칙) 커버리지가 오르므로 LLM 필요성이 더 줄어든다 |
| D6 통제 어휘로만 | **확장** | `facet_vocab`(초판)은 05 문서의 `vocab_term` 으로 **흡수**한다 — 축 값 사전과 도메인 용어 사전을 둘로 두면 동의어가 갈라진다. 초판 `facet_vocab` 테이블은 만들지 않는다(중복 제거) |

> **초판 §4.5 `facet_vocab` 은 폐기되고 05 문서의 `vocab_term` 으로 통합한다.**
> 구현 시 `facet_vocab` 을 만들지 말 것 — 같은 것을 두 곳에 두면 반드시 갈라진다(T39 CRZ).

### 8.5 갱신된 비기능 요구

| 항목 | 기준 | 근거 |
|---|---|---|
| CQG 평가 시간 | 데이터셋 1개 ≤ 1초 (8지표 전부 기존 프로파일 재사용) | 인제스트 동기 실행 상한 |
| REJECTED 조기 종료 | 자격 미달은 관계·주제 계산을 **하지 않는다** | 파이프라인 최대 비용 구간 회피(06 §5) |
| 표준 바인딩 | 데이터셋 1개 × 표준 20종 대조 ≤ 2초 | 사전 조회가 인덱스 기반이면 성립 |
| 사전 조회 | 컬럼 1개 매칭 ≤ 10ms | `idx_vocab_term` 필요 |
| 격리물 보존 | 무기한(삭제 없음). 10배 초과 시 정책 재검토 | 06 Q1 |
