# 06. 후보 자격 · 주/부 관계 · 표준 등재 승인 관리

> 세 가지 게이트를 다룬다. 셋 다 "들어오는 것을 그냥 쌓지 않는다"는 같은 원칙의 다른 적용이다.
>
> | 게이트 | 질문 | 통과 못 하면 |
> |---|---|---|
> | **CQG** 후보 자격 | 이게 데이터셋일 가치가 있는가 | 격리(삭제 아님) |
> | **PSR** 주/부 판정 | 같은 것을 다루는 표 중 무엇이 정본인가 | 부(secondary)로 강등 |
> | **SAG** 표준 등재 승인 | 이걸 전사 뼈대로 올려도 되는가 | draft 로 대기 |

---

# §1. 문제 — 왜 자격 게이트가 필요한가

현행 `DatasetIngestService` 는 **헤더처럼 보이는 행이 있으면 무조건 데이터셋을 만든다.**
그 결과 실제로 이런 것들이 데이터셋이 된다:

| 실제 유입물 | 왜 쓰레기인가 |
|---|---|
| 표지·목차 시트 | 컬럼이 `제목`,`값` 두 개뿐. 의미 관계 없음 |
| 범례·설명 시트 | 행이 설명 문장. 집계 대상이 아님 |
| 빈 양식 시트 | 헤더만 있고 데이터 0~2행 |
| 계산 보조 시트 | 중간 계산값. 맥락이 원본 시트에 있어 혼자서는 뜻이 없음 |
| 잘린 표 | 컬럼 절반이 빈 이름(`Column7`, `Unnamed`) |

이것들이 데이터셋 목록에 섞이면 **검색·분류·주제 군집이 전부 오염된다.**
쓰레기 100개가 진짜 20개를 덮는다.

# §2. CQG — 후보 자격 게이트 (Candidate Qualification Gate)

## 2.1 가치 8요소 → 측정 가능한 지표

사용자가 제시한 가치(단어의미·맥락·문장·주제·의미·역할·방향성·의도)를 **측정 가능한 것**으로
내린다. 추상어를 그대로 두면 구현할 수 없고, 구현할 수 없는 기준은 없는 기준이다.

| # | 가치 요소 | 측정 지표 | 배점 | 계산 |
|---|---|---|---|---|
| 1 | **단어 의미**(lexical) | 헤더 토큰의 어휘 사전 매칭률 | 15 | `사전매칭 컬럼 / 전체 컬럼` × 15 |
| 2 | **맥락**(context) | 출처·기준일·배치 식별 가능 | 10 | 3요소 중 채워진 수 / 3 × 10 |
| 3 | **문장·구조**(structure) | 헤더 존재 + 유효 컬럼명 비율 + 결측률 | 15 | `유효헤더율 × (1-결측률)` × 15 |
| 4 | **주제**(topic) | 컬럼들이 한 주제로 응집 | 10 | 군집 응집도 또는 사전 동일 도메인 비율 × 10 |
| 5 | **의미·역할**(role) | role 판정된 컬럼 비율 | 15 | `role≠text 컬럼 / 전체` × 15 |
| 6 | **기능 역할**(function) | 분야(domain) 판정 확신도 | 10 | domain confidence × 10 |
| 7 | **방향성**(direction) | 시간·상태 축 보유(변화를 담는가) | 10 | time 1개+ (5) + status 1개+ (5) |
| 8 | **의도**(intent) | 왜 만들어졌는지 알 수 있는 메타 | 15 | 시트명 유의미(5) + 출처파일 식별(5) + 설명·표준바인딩(5) |
| | | **합계** | **100** | |

**추가 조건 — 규모 하한** (점수와 별개의 필수 관문):
- 데이터 행 ≥ 3 · 유효 컬럼 ≥ 2 — 이 아래는 점수 계산 없이 즉시 `REJECTED`.
  행 2개짜리 표는 통계적 의미가 성립하지 않는다.

## 2.2 판정 3구간

| 점수 | 판정 | 처리 |
|---|---|---|
| **≥ 70** | `QUALIFIED` | 정식 데이터셋. 목록·검색·질의에 참여 |
| **40 ~ 69** | `PROVISIONAL` | **부 후보**. 목록에는 "보완 필요"로만 노출, 기본 질의에서 제외.<br>사람이 의미를 보강(설명·표준 바인딩·용어 등록)하면 재평가로 승격 |
| **< 40** | `REJECTED` | **격리(quarantine)**. 목록에서 숨김. 사유와 점수 내역을 남긴다 |

## 2.3 REJECTED는 삭제가 아니다 — 격리다

```sql
CREATE TABLE dataset_qualification (
  dataset_id   VARCHAR(60) PRIMARY KEY,
  verdict      VARCHAR(20) NOT NULL,      -- QUALIFIED | PROVISIONAL | REJECTED
  score        INTEGER NOT NULL,
  breakdown    VARCHAR(2000) NOT NULL,    -- 8요소 점수 JSON — 왜 이 점수인지 전부
  reason       VARCHAR(500),              -- 사람이 읽는 한 줄 ("헤더 2개, 데이터 1행")
  quarantined  BOOLEAN DEFAULT FALSE,
  override_by  VARCHAR(50),               -- 사람이 뒤집었으면 그 사람
  override_at  VARCHAR(20),
  evaluated_at VARCHAR(20)
);
```

**왜 지우지 않는가** — 세 가지 이유, 전부 실측 근거가 있다:

1. **오판정은 반드시 생긴다.** 8지표 전부 추정이다. 진짜 데이터를 쓰레기로 본 경우 되돌릴 길이 있어야 한다.
2. **원본이 이미 저장돼 있다.** `dataset_row` 에 적재된 뒤 평가하므로 지우는 것은 **추가 작업**이다.
   하지 않는 편이 더 싸다(ponytail).
3. **격리 목록 자체가 정보다.** "이 파일은 시트 12개 중 8개가 쓰레기" → 업로드 습관을 고칠 근거.

**사람이 뒤집을 수 있다**: `POST /api/dds/qualification/{id}/override` → `QUALIFIED` 고정.
자동 재평가는 override 된 건을 건드리지 않는다(어휘 사전의 `human` 원칙과 동일).

## 2.4 평가 시점

| 시점 | 동작 |
|---|---|
| 인제스트 직후 | 자동 평가 1회. 실패해도 적재는 성공(부분저하) |
| 어휘 사전 갱신 후 | 재평가 배치 — 사전이 늘면 1·4·6번 점수가 오른다 |
| 표준 바인딩 후 | 재평가 — 8번(의도) 점수가 오른다 |
| 사람이 요청 | `POST /api/dds/qualify` |

**사전이 자라면 어제의 쓰레기가 오늘의 데이터가 된다.** 이것이 재평가를 반드시 두는 이유다.

# §3. PSR — 주/부 데이터셋 관계 (Primary-Secondary Relation)

## 3.1 문제

같은 것을 다루는 표가 여러 개 들어온다 — 이건 예외가 아니라 **정상**이다:

```
"IA 화면목록" 이 3개 있다
  ├ 2026-08-31 전체본 252행  ← 이게 정본
  ├ 2026-07-15 과거본 213행     (구버전)
  └ "여신만 발췌" 41행           (부분집합)
```

주/부를 안 가리면 질의가 **같은 화면을 3번 센다.** 집계가 조용히 틀린다.

## 3.2 판정 — 같은 표준에 바인딩된 것끼리 겨룬다

주/부 판정의 전제는 **표준 바인딩**(04 문서)이다. 같은 `std_id` 를 가진 데이터셋들이 경쟁 집합이다.
표준에 안 붙은 데이터셋은 애초에 비교 대상이 없으므로 단독 primary 다.

**순위 점수 (0~100)**

| 지표 | 배점 | 근거 |
|---|---|---|
| CQG 점수 | 30 | 자격 점수 그대로 반영 |
| 표준 바인딩률(`bind_ratio`) | 25 | 표준을 더 온전히 담은 쪽 |
| 커버리지(행 수 / 경쟁 집합 최대 행 수) | 20 | 부분집합은 정본이 아니다 |
| 신선도(기준일 최신) | 20 | 최신 기준일이 정본 |
| 사람 지정 | ±100 | 사람이 정하면 그게 끝 |

```sql
-- 2026-09-24 rename: dataset_role → dataset_canon, role → canon (USS data_role 과 이름 충돌 해소, 21 §2)
CREATE TABLE dataset_canon (
  dataset_id  VARCHAR(60) PRIMARY KEY,
  std_id      VARCHAR(60),               -- 경쟁 집합의 키 (NULL이면 단독)
  canon       VARCHAR(20) NOT NULL,      -- primary | secondary | quarantine
  rank_score  INTEGER,
  reason      VARCHAR(500) NOT NULL,     -- "행수 41 < 252(부분집합), 기준일 동일"
  relation    VARCHAR(20),               -- subset | older_version | derived | variant
  parent_ds   VARCHAR(60),               -- 부일 때 어느 주에 딸리는가
  pinned_by   VARCHAR(50),               -- 사람이 지정했으면
  updated_at  VARCHAR(20)
);
```

## 3.3 부(secondary)의 4종 관계

| relation | 뜻 | 판정 신호 | 질의 취급 |
|---|---|---|---|
| `subset` | 주의 부분집합 | 행이 주에 포함, 컬럼 동일 | 기본 제외(중복). "부분 데이터 포함" 옵션 시 참여 |
| `older_version` | 과거 버전 | 기준일이 이르고 구조 동일 | 기본 제외. 시계열 비교 질의에서만 |
| `derived` | 주에서 파생·가공 | 컬럼이 주의 부분 + 집계 컬럼 | 기본 제외. 출처 추적용 |
| `variant` | 관점이 다름 | 컬럼 겹침 낮고 행 겹침 높음 | **기본 포함** — 다른 정보를 담고 있다 |

**`variant` 만 기본 포함인 이유**: 나머지 셋은 주에 이미 있는 정보의 중복이지만,
variant 는 같은 대상의 **다른 면**이라 빼면 정보가 사라진다.

## 3.4 질의에서의 기본값

```
GET /api/dds/views/{id}/data                → primary + variant 만 (중복 없는 답)
GET /api/dds/views/{id}/data?scope=all      → secondary 전부 포함 (출처 추적·비교용)
```

응답의 `sources` 에 각 데이터셋의 `canon` 을 항상 표기한다 — 사용자가 "왜 이 표는 빠졌나"를
확인할 수 있어야 한다. **조용히 빼지 않는다.**

# §4. SAG — 표준 등재 승인 관리 (Standard Approval Gate)

> 표준은 전사 뼈대다. 아무나 올리면 뼈대가 아니라 잡동사니가 된다.
> 반대로 아무도 못 올리면 뼈대가 굳어 죽는다. 이 절은 그 사이의 문을 정의한다.

## 4.1 등재 대상 3종

| 대상 | 신규 등재 | 업그레이드 등재 |
|---|---|---|
| 표준 데이터셋(`standard_dataset`) | 새 엔티티 정의 | 필드 추가·의미 변경 |
| 표준 필드(`standard_field`) | 기존 표준에 필드 추가 | required·role·단위 변경 |
| 표준 어휘(`vocab_term` level=STD) | 새 용어 | 정의·코드값 변경 |

## 4.2 자동 평가 5기준 (점수 100)

사람이 보기 전에 기계가 먼저 건다. 통과 못 하면 사람에게 가지도 않는다.

| # | 기준 | 배점 | 측정 | 미달 시 |
|---|---|---|---|---|
| 1 | **재사용성** | 25 | 2개 이상 데이터셋/도메인에서 실제 사용 | 표준이 아니라 로컬이다 |
| 2 | **안정성** | 20 | 정의 변경 없이 N일(기본 14) 이상 사용 | 아직 흔들린다. 더 쓰고 오라 |
| 3 | **의미 완결성** | 20 | `definition`+`intent`+`source` 3종 구비 | 반려(보완 요청) |
| 4 | **충돌 없음** | 20 | 기존 표준과 의미 중복·모순 없음 | 중복이면 **기존 확장**을 제안(신설 아님) |
| 5 | **하위호환** | 15 | 기존 바인딩이 깨지지 않는가 | MAJOR → 영향도 평가 필수 |

**자동 통과선 80점.** 80 미만은 자동 반려 + 사유. 80 이상이 사람 승인 대기열로 간다.

> 기준 4번이 제일 중요하다 — **중복 표준이 하나 생기면 그때부터 모든 질의가 두 갈래로 갈린다.**
> 유사도 검사에서 기존 표준과 필드 겹침 0.6 이상이면 "신설 대신 확장" 으로 자동 전환 제안한다.

## 4.3 승인 워크플로

```
  제안(propose)              누구나. 자동 또는 사람
      │   ├ 자동 제안: 승격 신호(어휘 usage_count, 도메인 반복 사용)
      │   └ 수동 제안: 화면에서 "표준으로 제안"
      ▼
  자동 평가(evaluate)        5기준 점수. <80 → 반려(사유 기록, 재제안 가능)
      ▼
  사람 검토(review)          영향도 리포트 첨부: 영향 데이터셋 N개, 바인딩 변화 M건
      │   ├ 승인 → published (version 확정, 재바인딩 배치 예약)
      │   ├ 보완 → draft 복귀 (무엇을 보완할지 명시)
      │   └ 반려 → rejected (사유 기록. 같은 제안 재신청 시 이력 표시)
      ▼
  발행(publish)              version+1, status=approved
                             MINOR → 자동 재바인딩 / MAJOR → 예약 후 별도 실행
```

```sql
CREATE TABLE std_proposal (
  prop_id      VARCHAR(60) PRIMARY KEY,   -- SP-yyyyMMdd-HHmmss-n
  kind         VARCHAR(20) NOT NULL,      -- new_dataset | new_field | new_term | upgrade
  target       VARCHAR(160),              -- 대상 std_id 또는 std_id.field_key
  payload      VARCHAR(8000) NOT NULL,    -- 제안 내용 JSON
  proposer     VARCHAR(50),               -- 사람 이름 또는 auto
  auto_score   INTEGER,
  auto_detail  VARCHAR(2000),             -- 5기준 점수 내역
  impact       VARCHAR(2000),             -- 영향 데이터셋·바인딩 변화 요약
  status       VARCHAR(20) NOT NULL,      -- draft|evaluated|review|approved|rejected|superseded
  decided_by   VARCHAR(50),
  decided_at   VARCHAR(20),
  reason       VARCHAR(1000),             -- 승인·반려 사유 — 빈 값 불가
  created_at   VARCHAR(20)
);
CREATE INDEX idx_proposal_status ON std_proposal (status, created_at);
```

## 4.4 업그레이드(버전 상승)의 추가 관문

MINOR(하위호환)와 MAJOR(파괴적)는 절차가 다르다.

| | MINOR | MAJOR |
|---|---|---|
| 예 | optional 필드 추가, 동의어 추가 | 필드 삭제, required 추가, 의미 변경 |
| 영향도 리포트 | 요약만 | **필수** — 영향 데이터셋 전수 + 바인딩 변화 + 롤백 절차 |
| 승인 | 오너 1인 | 오너 + 영향 도메인 오너 |
| 적용 | 자동 재바인딩 | **예약 후 명시 실행**. 구버전 병행 유지 기간 필요 |
| 롤백 | 버전 되돌림 | 구버전 바인딩 복원(구버전을 지우지 않았으므로 가능) |

**"몇 개가 깨지는지 모르는 채 표준을 바꾸지 않는다"** — 이 한 줄이 MAJOR 절차의 전부다.

## 4.5 승인 없이 되는 것 / 안 되는 것

| 자유 | 승인 필요 |
|---|---|
| L-USR 데이터셋 생성·수정·삭제 | 표준 데이터셋·필드 신설·변경 |
| LOCAL 어휘 등록 | STD 어휘 등재·정의 변경 |
| 뷰(저장된 질의) 생성 | 표준 관계(`standard_relation`) 추가 |
| CQG override(사람 판단) | MAJOR 업그레이드 적용 |
| 도메인 확장 필드 추가 | 도메인 → 표준 승격 |

# §5. 세 게이트의 실행 순서 (인제스트 파이프라인 확정판)

```
업로드
  │
  ├ L1 구조화        헤더 탐지 · 타입 추론                     [현행 그대로]
  ├ L2 정제          정규화 · 결측 · 중복                       [Phase 2]
  │
  ├ ★ 어휘 매칭      사전 조회 (05 문서 §6)                     ─┐
  ├ ★ 표준 바인딩    매핑률 계산 → std_id 결정 (04 문서 §2.2)    │ 셋이 서로를
  ├ ★ 6축 분류       domain/area/role/context/topic (01 문서)    │ 먹인다
  │                                                            ─┘
  ├ ★ CQG 평가       8요소 점수 → QUALIFIED/PROVISIONAL/REJECTED
  │     └ REJECTED → 격리. 여기서 파이프라인 종료(관계·주제 계산 안 함 = 비용 절약)
  │
  ├ ★ PSR 판정       같은 std_id 경쟁 집합에서 primary/secondary
  ├   관계 추론      dataset_link (표준 관계 없을 때만)
  ├   주제 군집      QUALIFIED 만 대상
  │
  └ 완료 → 목록·검색·질의 참여
```

**REJECTED 에서 조기 종료하는 것이 성능 설계의 핵심이다.** 쓰레기에 임베딩·군집을 돌리는 것이
이 파이프라인에서 가장 비싼 낭비다. 자격 판정을 관계·주제보다 **앞에** 둔 이유가 이것이다.

# §6. 설계 결정 (ADR)

| # | 결정 | 대안 | 이유 | 깨지는 조건 |
|---|---|---|---|---|
| Q1 | REJECTED는 격리, **삭제 안 함** | 자동 삭제 | 오판정 복구 + 이미 적재돼 있어 지우는 게 오히려 추가 작업 | 격리물이 원본의 10배가 되면 보존기간 정책 필요 |
| Q2 | 8요소를 **측정 지표로 환산** | 추상 기준 그대로 | 측정 못 하는 기준은 사람마다 다르게 적용된다 = 기준 없음 | 지표가 실제 품질과 어긋나면(오분류율 실측) 배점 재조정 |
| Q3 | 컷오프 70/40 | 단일 임계 | 중간지대(보완하면 쓸 수 있는 것)를 버리지 않기 위해 | 실측 후 분포가 한쪽에 몰리면 재조정 |
| Q4 | CQG를 관계·주제 **앞에** | 뒤에 | 쓰레기에 비싼 계산을 돌리지 않는다 | 없음 |
| Q5 | 주/부는 **표준 바인딩 기준** | 이름 유사도 | 이름은 거짓말한다(같은 시트명 다른 표 — 실제 사고 이력 있음) | 표준에 안 붙은 데이터셋끼리는 판정 불가 → 단독 primary 처리 |
| Q6 | secondary 중 `variant`만 기본 포함 | 전부 제외 / 전부 포함 | 나머지 셋은 중복, variant는 다른 정보 | variant 판정이 틀리면 중복 집계 — 판정 근거를 응답에 노출해 검증 가능하게 |
| Q7 | 표준 승인은 **자동평가 + 사람** 2단 | 사람만 / 자동만 | 사람만이면 병목, 자동만이면 중복·모순 표준 양산 | 제안이 주 20건 넘으면 도메인별 위임 필요 |
| Q8 | 중복 표준은 **기존 확장**으로 전환 제안 | 신설 허용 | 중복 표준 1개 = 모든 질의가 두 갈래 | 겹침 0.6 임계가 실제와 안 맞으면 조정 |
