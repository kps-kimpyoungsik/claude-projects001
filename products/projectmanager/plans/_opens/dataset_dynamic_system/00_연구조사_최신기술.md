# 00. 연구 조사 — 비정형 → 정형 데이터셋화 최신 기술 (2026)

조사 목적: `데이터 > 데이터셋` 메뉴가 지금은 **엑셀 시트 = 데이터셋 1개**로만 동작한다.
여기에 "분야·영역·관계·의미·맥락·주제" 6축 의미를 붙여 **요청에 따라 데이터셋을 동적으로 뽑는다**는
목표에 실제로 쓸 수 있는 기술만 추린다. (유행어 수집이 아니라 **채택/미채택 판정**이 산출물)

---

## 1. 조사 결과 요약 — 4개 계열

| 계열 | 핵심 기술 | 2026 상태 | 본 시스템 채택 |
|---|---|---|---|
| A. 스키마 기반 추출 | JSON Schema를 LLM에 강제 → 구조화 출력 + 검증 + 실패 복구 | 성숙. 벤치마크(LLMStructBench)로 문법/의미 정확도 분리 측정이 표준화 | **채택** — 단, 최후 수단(T3) |
| B. 레이아웃 인지 파싱 | 표·헤더·figure 경계를 인식해 자르는 파서 (Document AI Layout Parser, Camelot 계열) | 표 중심 문서에서 단순 분할 대비 유의미한 정확도 우위 | **부분 채택** — 엑셀은 불필요, PDF·워드 확장 시 필수 |
| C. 의미 군집·온톨로지 유도 | 임베딩 → UMAP → HDBSCAN → c-TF-IDF (BERTopic), 라벨만 LLM | LLM이 "클러스터 라벨링"만 맡는 하이브리드가 비용/품질 최적점으로 수렴 | **채택** — 주제축(topic) 산출 엔진 |
| D. 시맨틱 레이어 / 메타데이터 그래프 | 택소노미(어휘) + 온톨로지(관계) + 시맨틱 레이어(질의 시 추상화) 3층 분리 | 카탈로그·거버넌스의 사실상 표준 구조. LLM 환각 감소 목적이 주된 도입 동기 | **채택** — 본 설계의 뼈대 |

## 2. 계열별 상세 + 본 프로젝트 적용 판단

### A. 스키마 기반 추출 (Schema-Guided Extraction)
- **내용**: 추출 대상 스키마를 먼저 고정하고, LLM에는 "이 스키마를 채워라"만 시킨다.
  다회전 JSON 생성 → 스키마 검증 → 규칙 검사 → 실패분 후처리 복구의 4단 파이프라인이 정석.
- **핵심 교훈**: 평가를 **문법 유효성(JSON 파싱 성공)** 과 **의미 정확도(값이 맞는가)** 로 분리해야
  한다. 파싱만 성공하고 값이 틀린 사례가 실무 실패의 대부분.
- **적용**: 엑셀 표는 이미 정형이라 LLM이 필요 없다. LLM은 **① 헤더가 병합·다단인 난해 시트,
  ② 비고/검토내용 같은 자유서술 셀에서 항목을 뽑을 때**만 쓴다(T3 계층).

### B. 레이아웃 인지 파싱 + 청킹
- **내용**: 문서 구조(제목/표/목록)를 먼저 인식하고 그 경계로 자른다. 표가 많은 문서는
  전용 표 추출기(Camelot 등) → 구조 보존 청크 구성이 별도 트랙으로 필요.
- **late chunking / contextual retrieval**: 문서 전체를 먼저 임베딩한 뒤 토큰 임베딩을 자르거나
  (late chunking), 청크마다 설명 문장을 앞에 붙여 임베딩(contextual retrieval)해서
  "잘린 조각이 맥락을 잃는" 문제를 푼다.
- **적용**: 현 단계 입력은 xlsx 하나뿐 → **보류**. 단 설계에서 인제스트 어댑터 경계를 열어 두어
  PDF·DOCX 확장 시 파서만 끼우면 되도록 한다(Phase 4).

### C. 의미 군집 · 온톨로지 유도
- **내용**: BERTopic 4단(임베딩 → UMAP 축소 → HDBSCAN 군집 → c-TF-IDF 대표어) 후,
  LLM에는 "이 키워드와 대표 문서를 보고 사람이 읽을 라벨을 지어라"만 시킨다.
  LLM으로 유사 토픽을 반복 병합해 토픽 수를 줄이는 기법도 확립됨.
- **적용**: **주제축(topic)의 산출 엔진으로 채택**. 대상은 데이터셋 전체가 아니라
  텍스트 컬럼(결함내용·작업설명·검토내용)과 데이터셋 이름/컬럼명 시그니처.

### D. 시맨틱 레이어 3층 분리 (본 설계의 뼈대)
- **택소노미**: 통제 어휘 + 계층 (= 본 설계의 분야/영역/주제 축 값 사전)
- **온톨로지**: 개념·관계·제약의 형식 정의 (= 관계축 link type)
- **시맨틱 레이어**: 질의 시점 추상화 — 측정값·조인·정책을 업무 용어로 노출
  (= 본 설계의 **데이터셋 뷰(dataset_view)**)
- **핵심 교훈**: 메타데이터는 "문서로 적어두는 것"이 아니라 **질의 경로에 실제로 놓여야** 값을 한다.
  카탈로그가 검색 표면, 시맨틱 레이어가 질의 어휘를 제공할 때 LLM 환각이 줄어든다.

## 3. 채택하지 않은 것 (근거 명시)

| 미채택 | 이유 |
|---|---|
| 벡터 DB 별도 도입 (Pinecone/Weaviate 등) | 현 데이터 규모 수백~수천 행. PostgreSQL + pgvector 또는 **Jaccard/코사인 자바 계산**으로 충분. 운영 컴포넌트 1개 추가는 비용이 이득보다 큼 |
| 전 데이터 LLM 라벨링 | 비용·지연·환각. 규칙/통계로 결정 가능한 것이 실측상 대부분(컬럼명 시그니처가 매우 규칙적) |
| 그래프 DB (Neo4j 등) | 관계 축의 실제 카디널리티가 데이터셋 수십 개 규모. 관계 테이블 1개로 충분 |
| 실시간 스트리밍 인제스트 | 입력이 사람의 엑셀 업로드다. 배치로 족함 |

---

## 4. 결론 — 본 시스템이 가져갈 3대 원칙

1. **싼 것부터 (3계층 에스컬레이션)** — 규칙 → 통계/임베딩 → LLM. 위 계층에서 확신도가
   임계 이상이면 아래 계층을 호출하지 않는다.
2. **모든 의미 판정에 출처와 확신도를 남긴다** — `source ∈ {rule, stat, embed, llm, human}`,
   `confidence ∈ [0,1]`. 사람의 수정(human)이 항상 최우선이며 재분류로 덮이지 않는다.
3. **의미는 질의 경로에 놓는다** — 메타를 표로만 쌓지 않고, 데이터셋 뷰(저장된 질의)가
   그 메타를 필터로 쓰게 한다. 그래야 "요청에 따라 동적 추출"이 성립한다.
