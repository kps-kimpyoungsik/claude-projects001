# 04. 표준 데이터셋 구조 설계 — **전체 수집정보의 뼈대**

> 이 문서가 DDS의 **척추**다. 6축 의미(01_설계서)가 "이 표가 무엇에 관한 것인가"를 붙이는 것이라면,
> 표준 데이터셋은 **"그 무엇이 원래 어떤 모양이어야 하는가"** 를 먼저 정해 둔 것이다.
> 들어오는 모든 데이터는 이 뼈대에 **최대한 맞춰지고**, 맞지 않는 부분만 따로 관리된다.

---

## 1. 왜 뼈대가 먼저인가

뼈대 없이 축만 붙이면 이런 일이 벌어진다 — 실제로 흔한 실패다:

| 뼈대 없음 | 결과 |
|---|---|
| 표A는 `담당자`, 표B는 `PM`, 표C는 `책임자` | 셋이 같은 것인지 시스템이 모른다. 통합 질의 불가 |
| 표A의 `상태`는 5값, 표B의 `상태`는 12값 | 상태별 집계가 표마다 다른 뜻이 된다 |
| 새 엑셀이 올 때마다 새 구조 | 데이터셋 100개 = 구조 100개. 재사용 0 |

**표준 데이터셋은 "먼저 정해 둔 정답 모양"이다.** 들어온 표를 이 모양에 **바인딩**하면,
표가 몇 개든 질의는 하나로 통한다. 바인딩되지 않은 부분은 버리지 않고 확장 영역에 둔다.

## 2. 3층 계층 — 표준 / 도메인 / 사용자

```
  ┌──────────────────────────────────────────────────────────────┐
  │  L-STD  표준 데이터셋 (Standard)                              │
  │    전사 공통 뼈대. 승인 없이는 만들 수도 바꿀 수도 없다.       │
  │    예) STD-TASK(작업) · STD-SCREEN(화면) · STD-DEFECT(결함)   │
  │        STD-PERSON(인원) · STD-ISSUE(이슈)                     │
  └───────────────────────┬──────────────────────────────────────┘
                          │ 상속(필드 추가만 허용, 삭제·의미변경 금지)
  ┌───────────────────────┴──────────────────────────────────────┐
  │  L-DOM  도메인 데이터셋 (Domain)                              │
  │    특정 업무 도메인이 표준에 필드를 더한 것.                   │
  │    예) DOM-여신-SCREEN = STD-SCREEN + {여신등급, 심사단계}     │
  │    도메인 오너가 관리. 표준 승격 신청 가능.                    │
  └───────────────────────┬──────────────────────────────────────┘
                          │
  ┌───────────────────────┴──────────────────────────────────────┐
  │  L-USR  사용자 데이터셋 (User / Local)                        │
  │    개인이 올린 표. 승인 불필요, 자유롭게 만든다.               │
  │    표준에 바인딩되면 표준 질의에 자동 참여한다.                │
  └──────────────────────────────────────────────────────────────┘
```

### 2.1 계층별 규칙

| 항목 | L-STD 표준 | L-DOM 도메인 | L-USR 사용자 |
|---|---|---|---|
| 생성 | **승인 필수**(06 문서) | 도메인 오너 승인 | 자유 |
| 변경 | 버전 + 승인 (MAJOR는 영향도 평가) | 버전 + 오너 승인 | 자유 |
| 삭제 | **불가** — `deprecated` 로만 | deprecated | 자유 |
| 필드 추가 | 승인 | 자유(확장 영역) | 자유 |
| 상위 필드 의미 변경 | MAJOR 승인 | **금지** | **금지** |
| 질의 노출 | 전사 | 해당 도메인 | 소유자 + 공유 지정자 |

**핵심 불변식**: 하위 계층은 상위의 의미를 **덮어쓰지 못한다.** 더할 수만 있다.
이것이 깨지면 "같은 필드명이 계층마다 다른 뜻"이 되어 뼈대가 뼈대이기를 그만둔다.

### 2.2 "최대한 표준으로" — 바인딩 우선 원칙

인제스트할 때 순서는 고정이다:

```
① 표준 바인딩 시도   — 헤더를 표준 필드에 매핑 (어휘 사전 동의어 포함)
② 매핑률 계산        — 바인딩된 컬럼 / 전체 컬럼
③ 분기
   매핑률 ≥ 0.7  →  표준 데이터셋의 인스턴스로 등록 (std_id 바인딩)
                     바인딩 안 된 컬럼은 확장 필드(ext_*)로 보존
   0.4 ~ 0.7     →  부분 바인딩. 도메인 확장 후보로 표면화
                     "이 표는 STD-SCREEN 과 62% 일치합니다. 도메인 확장으로 등록할까요?"
   < 0.4         →  바인딩 없음. L-USR 로 두고 표준 제안 후보로만 기록
```

**매핑률이 낮다고 거부하지 않는다.** 거부는 후보 자격 게이트(06 문서)의 일이고, 여기는
"표준에 맞는가"만 본다. 둘은 다른 질문이다 — 표준에 없는 완전히 새로운 종류의 좋은 데이터가
있을 수 있다.

## 3. 표준 데이터셋의 실체 — 3개 정의 테이블

표준은 "컬럼 목록"이 아니라 **의미 필드의 집합**이다. 물리 타입이 아니라 역할·단위·어휘를 담는다.

```sql
-- 3.1 표준 데이터셋 정의 (엔티티)
CREATE TABLE standard_dataset (
  std_id       VARCHAR(60) PRIMARY KEY,   -- STD-TASK, STD-SCREEN, DOM-여신-SCREEN
  level        VARCHAR(10) NOT NULL,      -- STD | DOM | USR
  parent_std   VARCHAR(60),               -- DOM 이 상속하는 STD (level=STD 면 NULL)
  name         VARCHAR(200) NOT NULL,
  domain       VARCHAR(100),              -- 6축의 domain 값과 같은 어휘를 쓴다
  purpose      VARCHAR(1000) NOT NULL,    -- 이 엔티티가 무엇을 담는가 (의도)
  grain        VARCHAR(200) NOT NULL,     -- 1행이 무엇 1건인가 ("화면 1개", "결함 1건")
  owner        VARCHAR(100),
  version      VARCHAR(20) NOT NULL,      -- semver
  status       VARCHAR(20) NOT NULL,      -- draft | review | approved | deprecated
  created_at   VARCHAR(20),
  updated_at   VARCHAR(20)
);

-- 3.2 표준 필드 정의 (의미 필드)
CREATE TABLE standard_field (
  std_id       VARCHAR(60) NOT NULL,
  field_key    VARCHAR(100) NOT NULL,     -- 시스템 키 (영문 snake). 화면 표기와 분리
  label        VARCHAR(200) NOT NULL,     -- 사람이 보는 이름
  role         VARCHAR(20) NOT NULL,      -- 01 설계서의 role 8종 (id/time/status/measure/...)
  data_type    VARCHAR(20) NOT NULL,      -- number | date | code | text | bool
  required     BOOLEAN DEFAULT FALSE,     -- 이 필드 없이는 이 표준이라 할 수 없다
  unit         VARCHAR(30),               -- 원, %, 일, 건 — 단위 없는 수치는 의미가 없다
  code_set     VARCHAR(100),              -- 값이 코드면 그 코드집합 id (어휘 사전 참조)
  definition   VARCHAR(1000) NOT NULL,    -- 무엇인가
  intent       VARCHAR(500),              -- 왜 필요한가 (의도 보존)
  synonyms     VARCHAR(1000),             -- 바인딩에 쓰는 동의어 (어휘 사전과 동기)
  is_ext       BOOLEAN DEFAULT FALSE,     -- DOM 이 추가한 확장 필드인가
  PRIMARY KEY (std_id, field_key)
);

-- 3.3 표준 간 관계 (엔티티 레벨 온톨로지 — 6축의 link 와 층이 다르다)
CREATE TABLE standard_relation (
  std_from     VARCHAR(60) NOT NULL,
  field_from   VARCHAR(100) NOT NULL,
  std_to       VARCHAR(60) NOT NULL,
  field_to     VARCHAR(100) NOT NULL,
  cardinality  VARCHAR(10),               -- 1:1 | 1:N | N:1 | N:N
  meaning      VARCHAR(300) NOT NULL,     -- "결함은 화면에 대해 제기된다"
  PRIMARY KEY (std_from, field_from, std_to, field_to)
);
```

**`standard_relation` 과 `dataset_link`(01 설계서)의 차이 — 혼동하면 설계가 무너진다**

| | `standard_relation` | `dataset_link` |
|---|---|---|
| 층 | **정의(type) 층** — "결함은 화면에 달린다"는 규칙 | **인스턴스 층** — "이 표와 저 표가 실제로 값이 겹친다" |
| 출처 | 사람이 정의, 승인 대상 | 자동 추론(Jaccard) |
| 쓰임 | 조인 경로의 **정답** | 정답이 없을 때의 **추정** |
| 우선 | 표준 관계가 있으면 **그것을 쓴다** | 표준 관계가 없을 때만 |

질의 계획(03 기능정의서 3-2)은 **표준 관계를 먼저 보고**, 없을 때만 추론 링크로 내려간다.
추론이 정의를 이기지 않는다.

## 4. 실제 데이터셋 ↔ 표준 바인딩

```sql
-- 데이터셋이 어느 표준의 인스턴스인가
ALTER TABLE dataset ADD COLUMN IF NOT EXISTS std_id      VARCHAR(60);
ALTER TABLE dataset ADD COLUMN IF NOT EXISTS bind_ratio  DOUBLE PRECISION;  -- 매핑률
ALTER TABLE dataset ADD COLUMN IF NOT EXISTS level       VARCHAR(10);       -- STD | DOM | USR

-- 컬럼 하나하나가 어느 표준 필드에 붙었는가
CREATE TABLE dataset_binding (
  dataset_id  VARCHAR(60) NOT NULL,
  col_name    VARCHAR(200) NOT NULL,
  std_id      VARCHAR(60) NOT NULL,
  field_key   VARCHAR(100) NOT NULL,
  confidence  DOUBLE PRECISION,
  source      VARCHAR(10),               -- rule(동의어 일치) | stat | llm | human
  evidence    VARCHAR(500),              -- "동의어 '담당자'→person_name 일치"
  PRIMARY KEY (dataset_id, col_name)
);
CREATE INDEX idx_binding_std ON dataset_binding (std_id, field_key);
```

**바인딩되면 무엇이 달라지는가** — 이게 뼈대의 값어치다:

1. **통합 질의** — `STD-DEFECT` 로 질의하면 그 표준에 바인딩된 **모든** 데이터셋이 한 번에 걸린다.
   컬럼명이 `담당자`든 `PM`이든 상관없다.
2. **의미 검증** — `required` 필드가 없으면 "이 표는 STD-DEFECT 를 자처하지만 결함ID가 없다"를
   자동으로 잡는다.
3. **단위·코드 통일** — `unit`·`code_set` 이 정의돼 있으므로 집계가 뒤섞이지 않는다.
4. **주/부 판정 근거** — 같은 표준에 바인딩된 데이터셋끼리 비교가 성립한다(06 문서 §3).

## 5. 초기 표준 5종 (실측 기반 — 상상으로 만들지 않는다)

현행 DB에 실제로 있는 것에서 뽑는다. `wbs_task`·`ia_screen`·`defect` 는 이미 정형화돼 있어
그 자체가 표준 후보다.

| std_id | grain(1행 = ?) | 핵심 필드(required) | 출처 실측 |
|---|---|---|---|
| `STD-TASK` | 작업 1건 | `task_name`, `dep`, `plan_start`, `plan_end`, `progress` | `wbs_task` 23컬럼 |
| `STD-SCREEN` | 화면 1개 | `screen_id`, `depth_path`, `dev_status` | `ia_screen` 15컬럼 |
| `STD-DEFECT` | 결함 1건 | `defect_id`, `reg_dt`, `status`, `content` | `defect` 25컬럼 |
| `STD-PERSON` | 인원 1명 | `person_name`, `role`, `part` | `투입인력` 시트 |
| `STD-ISSUE` | 이슈 1건 | `issue_no`, `content`, `done_yn` | `이슈페이지` 시트 |

표준 관계 초기 4건:
```
STD-DEFECT.req_id     → STD-SCREEN.screen_id   N:1  "결함은 화면에 대해 제기된다"
STD-TASK.owner        → STD-PERSON.person_name N:1  "작업에는 담당자가 있다"
STD-SCREEN.owner      → STD-PERSON.person_name N:1  "화면에는 담당자가 있다"
STD-ISSUE.related_wbs → STD-TASK.task_id       N:1  "이슈는 작업에서 발생한다"
```

이 4건은 **이미 코드에 암묵적으로 존재한다**(`DefectService` 가 `req_id` 로 IA 를 찾는다).
표준 관계로 올린다는 것은 **코드에 숨어 있던 지식을 데이터로 꺼내는 일**이다 — 새로 만드는 게 아니다.

## 6. 버전과 하위호환

```
MAJOR  필드 삭제 · required 추가 · 의미(definition) 변경 · role 변경
       → 기존 바인딩이 깨질 수 있다. 영향도 평가 필수(06 문서 §4)
MINOR  필드 추가(optional) · 동의어 추가 · 관계 추가
       → 기존 바인딩 무영향. 자동 재바인딩만 수행
PATCH  label·설명 문구 수정
       → 영향 없음
```

**MAJOR 승인 시 필수 산출**: 영향받는 데이터셋 목록 + 각각의 바인딩 변화 + 롤백 방법.
"몇 개가 깨지는지 모르는 채" 표준을 바꾸지 않는다.

**구 버전 보존**: `standard_field` 는 버전별로 남긴다(삭제 없음). 과거 데이터셋은 과거 버전에
바인딩된 채로 유효하며, 재바인딩은 명시적 작업이다 — 자동으로 과거를 고쳐 쓰지 않는다.

## 7. 설계 결정 (이 문서의 ADR)

| # | 결정 | 대안 | 이유 | 깨지는 조건 |
|---|---|---|---|---|
| S1 | 표준은 물리 컬럼이 아니라 **의미 필드** | 표준 테이블을 실제로 만들기 | 들어오는 표는 모양이 제각각이다. 물리 스키마를 강요하면 대부분이 적재 불가가 된다 | 표준 인스턴스가 수백만 행이 되어 JSON payload 성능이 한계에 닿을 때 |
| S2 | 바인딩은 **느슨**(매핑률 0.7) | 100% 일치만 인정 | 실데이터는 항상 컬럼이 남거나 모자란다. 엄격하면 아무것도 안 붙는다 | 오바인딩(다른 표준에 잘못 붙음)이 실측 5% 넘으면 임계 상향 |
| S3 | 하위 계층은 **더하기만** | 오버라이드 허용 | 오버라이드를 허용하면 같은 필드명이 계층마다 다른 뜻이 된다 = 뼈대 소멸 | 도메인이 표준을 진짜로 못 쓰는 사례가 나오면 그건 표준이 틀린 것 → 표준을 고친다 |
| S4 | 표준 관계가 추론 링크보다 **우선** | 점수 높은 쪽 | 사람이 정의한 것이 통계보다 정확하다. 추론은 정의가 없을 때의 대용품 | 표준 관계가 낡아 실제와 어긋나면 → 그 자체가 표준 개정 신호 |
| S5 | 초기 표준은 **실측 3테이블에서** | 업계 표준 모델 도입 | 이 시스템의 실제 데이터가 근거다. 외부 모델은 안 맞는 필드가 더 많다 | 외부 시스템과 데이터를 주고받게 되면 그때 매핑 계층 추가 |
| S6 | 표준 삭제 **불가**(deprecated만) | 미사용 표준 삭제 | 과거 데이터셋의 바인딩이 고아가 된다. 되돌릴 길이 없다 | 없음 — 보존 비용이 무시 가능(정의 몇 행) |

### 9.1 학습이란 무엇인가 — 이 구현의 정의

신경망이 아니라 **관측·교정이 쌓이면 다음 판정이 달라지는 것**이다. 지금 규모(데이터셋 6개·
헤더 40개)에서 신경망은 학습할 재료가 없다. 대신 3층이 실제로 자란다:

| 층 | 무엇 | 확신도 | 자라는 방식 |
|---|---|---|---|
| **L2 교정** | 사람이 고친 바인딩 | 1.0 | 한 번 고치면 그 표기는 **영구히** 그 필드로. 자동 판정이 덮지 못한다 |
| **L1 통계** | 같은 표기가 어느 필드에 몇 번 붙었나 | 0.6 → 0.95 | 관측이 쌓일수록 오르되 **1.0 에 닿지 않는다**(통계는 사람이 아니다) |
| **L0 규칙** | 어휘 사전 동의어 일치 | 0.9 | 사전이 자라면 인식 범위가 함께 자란다(Phase 1 연동) |

판정 순서는 **L2 → L1 → L0**. 순서가 뒤집히면 사람이 고친 것을 규칙이 다시 덮어 교정이
무의미해진다. `binding_feedback` 이 학습 저장소이고, 사람 교정은 자동 관측의 **10배 가중**이다.

**임베딩은 넣지 않았다.** `BindingEngine.semanticScore()` 자리만 있고 `null` 을 돌려준다
(T102 NTM Port). 모델 없이 자리만 채우면 "있는 척"이 되고, 지금 규모는 c-TF-IDF 로 충분하다는
것이 00 연구조사의 판정이다. 조달되면 이 한 메서드만 구현하면 L1 과 L0 사이에 끼워진다.

### 9.2 실측 결과 — 표준은 섰고, 실데이터는 아직 안 붙는다

| 항목 | 결과 |
|---|---|
| 표준 5종 | 전부 시드 (필드 31개 · required 15개 · grain 전건 명시) |
| 표준 관계 4건 | 코드에 숨어 있던 조인 지식을 데이터로 꺼냄 |
| 실데이터 6개 바인딩 | **STD 0 · DOM 0 · USR 6** (최고 매핑률 0.19) |

**이것은 버그가 아니라 정확한 판정이다.** 표준 5종은 `wbs_task`·`ia_screen`·`defect` **DB
테이블** 구조에서 도출했는데, `dataset` 에 적재된 6개는 전혀 다른 엑셀 시트다(통합테스트 대응
업무분장·제·개정 이력 등). 억지로 붙였다면 ADR S2 가 경계한 오바인딩이 됐을 것이다.

바인딩이 실제로 작동한다는 근거는 테스트에 있다 — 결함 형태의 표를 넣으면 `STD-DEFECT` 에
**0.83** 으로 붙고, 절반만 맞으면 `DOM`(도메인 확장 후보), 전혀 안 맞으면 `USR` 로 간다.

### 9.3 학습 루프 닫힘 (2026-09-16)

화면 `데이터 > 표준 데이터셋`(3탭: 표준 뼈대 · **바인딩 교정** · 학습 현황)으로 사람이
직접 고칠 수 있게 되면서 루프가 닫혔다. 실서버 검증:

```
교정 "구분" → STD-ISSUE.content
  → 학습 기록 human=1 (자동 관측의 10배 가중)
  → 재바인딩 후에도 source=human, confidence=1.0 로 유지
```

**화면을 붙이는 과정에서 결함 3건이 드러났다** — 실제로 클릭해 보기 전에는 안 보였다:

| 결함 | 무엇이 잘못됐나 | 조치 |
|---|---|---|
| **자리표시자 학습** | `col1`(헤더가 비어 우리가 붙인 이름)을 교정 대상으로 받아들였다. 학습하면 **무관한 표들이 같은 필드로 묶인다** | `correct()` 에서 거부. T115 SSI 가 사전 수집에서 거른 것과 같은 이유인데 교정 경로에만 필터가 없었다 |
| **교정이 재바인딩에서 사라짐** | `bind()` 가 득표 1위 표준의 바인딩만 저장해, 사람이 **다른 표준으로** 고쳐 두면 그 교정이 버려졌다 — L2 우선 원칙이 이 경로에서만 깨져 있었다 | human 바인딩은 득표와 무관하게 보존 |
| **되돌릴 수 없는 학습** | 잘못 배운 것을 지울 방법이 전혀 없었다. 사람 교정이 자동 판정을 덮으므로 틀린 교정은 **스스로 풀리지 않는다** | `DELETE /api/dds/learned/{colNorm}` — 되돌리기 없는 학습은 학습이 아니라 각인이다 |

테스트 45/45 (신규 3건이 위 결함을 각각 못박는다).

### 9.4 남은 것

  지금은 "도메인 확장 후보"로 표시만 한다.
- `wbs_task`·`ia_screen`·`defect` 는 Core 경로로 적재돼 `dataset` 에 없다. 이들을 표준
  인스턴스로 노출할지는 별도 판단(노출하면 표준 바인딩의 첫 실사례가 생긴다).

## 10. 도메인 데이터셋(DOM) 구현 (2026-09-16, Cycle 3)

`DomainBuilder` — 미바인딩 컬럼을 확장 필드로 삼아 `DOM-{도메인}-{부모}` 를 만든다.
테스트 `DomainBuilderTest` 6건, 전체 **51/51**.

### 10.1 상속에서 필드를 복제하지 않는다

DOM 을 만들 때 부모 STD 필드를 복사해 두면 편하지만, **부모가 바뀌어도 자식이 따라가지
않는다.** 정의가 두 벌이 되고 갈라지면 같은 이름이 계층마다 다른 뜻이 되어 §2.1 불변식이
깨진다. 그래서 DOM 테이블에는 **확장 필드만** 저장하고 조회 시점에 합친다.

테스트가 이를 못박는다 — 부모에 필드를 추가하면 자식 조회 결과가 즉시 함께 늘어난다.

### 10.2 하위는 더할 수만 있다 (ADR S3 강제)

부모에 이미 있는 `field_key` 는 확장으로 받지 않는다. 오버라이드를 허용하면 상위 의미를
덮게 되고, 그 순간 뼈대가 뼈대이기를 그만둔다.

### 10.3 표준 승격 제안 — 제안만 한다

같은 확장 필드를 **2개 이상 도메인**이 쓰면 그건 도메인 고유가 아니다 → 승격 후보로 표면화.
올리는 것은 사람이다(05 ADR V5 와 같은 이유). 승격하면 **모든 하위가 상속받으므로** 되돌리기가
비싸다.

### 10.4 실데이터 검증은 하지 못했다 — 대상이 없다

| 항목 | 결과 |
|---|---|
| 구현·테스트 | DOM 생성·상속·오버라이드 차단·승격 제안·부모 없음 거부 **6/6 통과** |
| 실데이터 적용 | **0건** — 6개 데이터셋이 전부 USR(매핑률 0.4 미만)이라 DOM 후보 자체가 없다 |

**3사이클 연속 같은 벽이다.** Phase 2 기능(바인딩·학습·도메인)을 쌓았지만 실데이터에서는
한 번도 작동하지 못했다. 원인은 §9.2 그대로 — 표준 5종은 `wbs_task`·`ia_screen`·`defect`
**DB 테이블**에서 도출했는데, `dataset` 에 적재된 6개는 전혀 다른 엑셀 시트다.

기능을 더 쌓기 전에 **이 벽을 깨는 것이 먼저다**(§AQG Q-C2 — 같은 구간만 반복 개선하지 않는다).
정형 3테이블을 `dataset` 으로 노출하면 표준 바인딩의 첫 실사례가 생긴다.

## 11. 벽 깨기 — 정형 테이블 뷰 (2026-09-16, Cycle 4)

3사이클 연속 실데이터 바인딩 0건이던 벽을 깼다.

### 11.1 복사가 아니라 뷰

`wbs_task`·`ia_screen`·`defect` 를 `dataset_row` 로 **복사하지 않는다.** 복사하면 같은 사실이
두 벌이 되고 원본이 바뀌어도 사본은 그대로다 — T115 SSI 가 막는 원천 중복이다.

`CoreView` 는 `dataset` · `dataset_column` **메타만** 등록하고, 행은 원본 테이블에서 읽는다
(`DatasetWriter.rows()` 가 `DS-VIEW-` 접두를 보고 분기). 바인딩은 컬럼명만 보므로 이것만으로
표준에 붙는다.

컬럼은 **사람이 보는 한글 이름**으로 노출한다(`owner`→`담당자`). 표준이 이 테이블들에서
도출됐으므로 표준 label 과 같은 건 우연이 아니라 당연하다.

### 11.2 실측 — 벽이 깨졌다

| 데이터셋 | 표준 | 매핑률 | 판정 |
|---|---|---|---|
| `DS-VIEW-defect` | STD-DEFECT | **0.62** (8/13) | DOM |
| `DS-VIEW-ia_screen` | STD-SCREEN | **0.60** (6/10) | DOM |
| `DS-VIEW-wbs_task` | STD-TASK | **0.53** (8/15) | DOM |

이어서 DOM 생성까지 완주 — `DOM-품질-DEFECT`(확장 5) · `DOM-일정-TASK`(확장 7) ·
상속 8 + 확장 7 = 15 필드 · **표준 승격 제안 1건**(`비고` 가 2개 도메인에서 반복).

### 11.3 실측이 드러낸 결함 — 맥락 없는 통계 고정

첫 측정에서 `담당자` 가 **미바인딩**이었다. `담당자` 는 STD-TASK 에도 STD-DEFECT 에도
정당하게 있는데, 앞선 통계 학습이 STD-TASK 로 고정해 결함 표에서 버려진 것이다.

**공통 표기는 여러 표준에 정당하게 존재한다** — 맥락 없이 하나로 고정하면 안 된다.
`bind()` 를 2패스로 고쳤다:

```
1패스  맥락 없이 해석 → 이 표가 어느 표준 쪽인지 정한다
2패스  정해진 표준을 맥락으로 주고 다시 해석
       → 이 표의 표준에 같은 표기가 있으면 그쪽으로 붙는다
```

판정 우선순위는 **사람 교정 > 맥락 > 통계 > 규칙**. 맥락이 사람을 이기면 교정이 무의미해지므로
맥락 분기 전에 human 여부를 먼저 본다.

결과: 0.54→**0.62**, 0.50→**0.60**.
