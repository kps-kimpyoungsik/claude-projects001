## 2026-09-13 처리 결과 (DDS Phase 0 — 성능 선행 정리)

`plans/_works/_opens/dataset_dynamic_system/` 설계의 Phase 0. 뷰 질의가 같은 조회 경로를 쓰게 되므로 먼저 처리했다.

**해결**
- **P1 #6 일부** — 미리보기 조회가 전 행을 올린 뒤 잘랐다(`DashboardService.rows()` → `datasets.rows()` 전량).
  `DatasetWriter.rows(id, limit)` 신설로 **DB에서 자른다**. 200행 요청에 수만 행을 올리지 않는다.
- **P1 #6 나머지(위젯 집계)** — 집계는 구조상 전 행이 필요해 SQL로 내리지 않았다(payload JSON 파싱이
  H2·PostgreSQL 공통 문법 없음). 대신 `MAX_AGGREGATE_ROWS=50,000` **상한 가드**를 넣어 초과 시
  **그 위젯만** 오류 표시하고 나머지는 그린다(기존 부분저하 패턴 유지). 근본 해소는 별도 작업.
- **P1 #7 해소** — `findRow()` 가 전량 로드 후 선형 탐색이었다. payload의 `"컬럼":"값"` 조각으로
  DB에서 후보를 좁힌 뒤 자바에서 정확 판정한다. LIKE 는 후보를 넓힐 뿐이라 결과는 전량 스캔과 동일.
  H2·PostgreSQL 기본 LIKE escape(`\`) 때문에 값에 따옴표가 있으면 못 찾던 문제까지 포함해 처리.
- `DatasetWriter.forEachRow()` 신설 — 값 목록 집계(`values()`)가 전 행 List를 만들지 않는다.

**검증**: `./mvnw -o test` → 17/17 통과 (기존 13 + 신규 `DatasetWriterQueryTest` 4). 기존 테스트 회귀 0.

**남은 것**
- **P0 #3(인증 0) 미해결** — DDS Phase 3(뷰 발행·삭제 API)의 착수 전제다. 방식(API Key 헤더 vs
  사내망 한정 배포) 결정 필요. 결정 전 Phase 3 착수 금지.
- 위젯 집계의 SQL 이관 — 상한 가드는 폭발만 막는다. 실제로 5만 행을 넘는 업로드가 생기면 그때.

**실측**: 쓰기 엔드포인트 **28개가 전부 무인증**이었다 — 전량 교체 2(`/api/admin/import`·

**구현**
- `ApiKeyFilter` — POST/PUT/DELETE/PATCH + `/api/` 경로에만 `X-API-Key` 검사.
  읽기(GET)는 막지 않는다: 조회까지 막으면 불편이 키 공유를 부른다.

- 프론트: `api.js` 에 `authHeaders()` 하나를 두고 나머지가 그걸 쓴다. 쓰기 헬퍼가 화면마다
  따로 있어(api.js·Dashboards·Defects) 각자 붙이면 반드시 한 곳을 빠뜨린다 — Cycle 6에서
  같은 이유로 4번 반복한 결함을 겪었기에 **키 로직만은 원천 하나**로 뒀다.
- CORS `allowedHeaders` 에 `X-API-Key` 명시(없으면 브라우저가 preflight 에서 막는다).

**검증**: **68/68** (기존 60 + `ApiKeyFilterTest` 8 — 비활성·활성·읽기·preflight·잘못된 키·
경로 밖까지 전 분기). 실서버 키 활성 모드로 9케이스 실측 — **전부 기대와 일치**.
