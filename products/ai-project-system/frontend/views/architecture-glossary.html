HA(고가용성)/이중화 구성이란

단일 서버(WEB 또는 WAS 1대)로만 서비스를 운영하면, 그 서버가 다운되거나 점검(재시작·배포) 되는 순간 서비스 전체가 중단됩니다. HA(High Availability, 이중화)는 서버를 2대 이상 두고 한쪽이 죽어도 다른 쪽이 요청을 이어받아 처리하도록 만드는 구성입니다 — 즉 "단일 장애점 (Single Point of Failure) 제거"가 핵심 목적입니다.

HA 관리 방식 비교 (관리 난이도·비용 순)

방식동작 개념관리 난이도비용적합한 경우
Keepalived + VIP 가상 IP(VIP)를 두 서버가 공유하고, 헬스체크로 살아있는 서버 쪽으로만 트래픽을 보냄 (VRRP 프로토콜) 낮음 낮음 서버 2대 규모의 소규모 이중화, 별도 로드밸런서 장비 없이 빠르게 구성하고 싶을 때
Pacemaker + Corosync 클러스터 리소스 매니저(Pacemaker)가 여러 서버의 상태를 감시·조율하고, Corosync가 노드 간 통신을 담당 — 리소스(서비스·DB·IP) 단위로 정교한 failover 규칙 정의 가능 중간~높음 낮음~중간 DB·다중 서비스가 얽힌 복잡한 클러스터, 세밀한 failover 정책이 필요할 때
클라우드 LB (ALB/NLB 등) 클라우드 사업자가 제공하는 관리형 로드밸런서가 헬스체크·트래픽 분산을 대신 처리 가장 낮음 종량제(사용량 비례) 클라우드(AWS/NCP/Azure 등) 환경, 직접 이중화 소프트웨어를 운영할 인력이 부족할 때

WebSocket + Redis(백플레인)이 이중화 환경에서 왜 필요한가

WebSocket은 서버와 브라우저 간 연결을 계속 유지하며 실시간으로 메시지를 주고받는 방식입니다. 문제는 WAS가 2대 이상(이중화)일 때 발생합니다 — 사용자 A는 WAS-1에, 사용자 B는 WAS-2에 WebSocket으로 연결돼 있으면, WAS-1에서 발생한 이벤트를 WAS-2에 연결된 사용자 B에게 그냥은 전달할 방법이 없습니다(각 WAS 프로세스가 자기 메모리 안의 연결만 알기 때문).

이 문제를 푸는 것이 백플레인(backplane)입니다 — 모든 WAS 인스턴스가 공통으로 구독하는 메시지 채널(Redis Pub/Sub 또는 NATS)에 이벤트를 발행하면, 그 채널을 구독 중인 모든 WAS가 이벤트를 받아 각자 자신에게 연결된 사용자에게 전달합니다. 단일 서버 구성이면 이 문제 자체가 생기지 않으므로 백플레인이 필요 없습니다("사용 안 함"이 정답인 경우).

단일 구성(백플레인 불필요): [사용자] ── WebSocket ── [WAS(1대)] 이중화 구성(백플레인 필요): [사용자A] ─ WS ─ [WAS-1] ─┐ ├─▶ [Redis Pub/Sub] ◀─┐ [사용자B] ─ WS ─ [WAS-2] ─┘ │ ▲───────── 이벤트 전파 ────────┘

HTTP vs HTTPS(SSL/TLS)

HTTP는 브라우저와 서버 사이를 오가는 데이터를 암호화하지 않고 그대로 전송합니다 — 같은 네트워크 상의 제3자가 패킷을 가로채면 로그인 정보·개인정보가 그대로 노출될 수 있습니다. HTTPS는 TLS(SSL의 후속 표준)로 그 구간을 암호화해, 가로채더라도 내용을 읽을 수 없게 만듭니다. 로그인·개인정보 입력이 있는 화면은 HTTPS가 사실상 필수입니다.

자체서명(self-signed) 인증서 vs 공인(Public CA) 인증서

구분발급 주체브라우저 신뢰적합한 경우
자체서명 (openssl 등으로 직접 생성) 내가 직접 서명 신뢰 안 함 — 브라우저가 "안전하지 않음" 경고 표시 내부망 전용 개발/테스트 환경
공인 인증서 (Let's Encrypt 등) 공인 인증기관(CA)이 서명 신뢰함 — 경고 없이 자물쇠 아이콘 표시 실제 사용자가 접속하는 운영 환경(외부 공개 서비스)

비밀번호 저장 — 해시 알고리즘 비교

비밀번호는 원문 그대로 저장하지 않고 해시(되돌릴 수 없는 변환값)로 저장합니다. 그런데 해시 알고리즘마다 "얼마나 대입 공격(brute-force)에 강한가"가 다릅니다 — 이 프로젝트의 보안 레벨 선택 화면(§8-5)에서 SHA-256을 기본값으로 두고 있지만, 아래 내용을 정직하게 알려드립니다(과장도 은폐도 하지 않습니다, T98 AIP).

DMZ(비무장지대)

외부 인터넷과 내부 시스템 사이에 두는 완충 구역입니다. 외부 공격자가 이 구역의 서버를 뚫어도, 바로 내부 핵심 시스템까지는 갈 수 없게 하는 안전지대 역할을 합니다.

중계서버(Relay/Gateway)

외부에서 온 요청을 대신 받아서, 검증한 뒤 내부 시스템에 전달해주는 대리인 서버입니다. 외부가 내부 DB에 직접 말을 걸 수 없게 하는 유일한 통로입니다 — 이 프로젝트에서는 role을 "GW"(게이트웨이/연계)로 등록한 서버만 DB로 향하는 허용 규칙의 출발점이 될 수 있습니다.

화이트리스트(허용목록)

"이 IP와 이 포트로만 들어올 수 있다"고 미리 정해둔 목록입니다. 목록에 없는 접근은 자동으로 거부되어, 실수나 침입으로 엉뚱한 경로가 열리는 것을 막습니다. 등록한 허용 규칙의 포트가 실제 서버가 열어둔 포트 범위를 벗어나면 등록 화면에서 바로 오류로 표시됩니다.

SSL/HTTPS 강제

외부에 공개되는 서버는 반드시 암호화된 통신(HTTPS)만 쓰도록 강제하는 것입니다. 암호화가 없으면 중간에서 누군가 통신 내용을 훔쳐보거나 조작할 수 있습니다(위 보안 기술 절 참고).
